# トラブルシューティングガイド

[English](../en-US/troubleshooting.md) | [中文](../zh-CN/troubleshooting.md)

本書では、よくある問題を症状別に挙げています。まずサービスログ、ブラウザーコンソール、および `/api-docs` での API レスポンスを確認してください。

## ページにアクセスできない

確認事項：

- サービスが起動しているか。
- ポートが使用されていないか。
- 設定で HTTPS が有効になっているか。
- アクセスしているプロトコルが正しいか。

デフォルト設定でよく使われるアドレス：

```text
https://127.0.0.1:8080/
```

自己署名証明書を使用している場合、ブラウザーは信頼されていないと警告します。手動で続行してアクセスする必要があります。

## ログインに失敗する

確認事項：

- RBAC ユーザーのパスワードが正しいか（デフォルトは `admin`。初回起動時のパスワードはコンソール出力を参照）。
- パスワード変更後に古いセッションが無効になっており、再ログインが必要ではないか。
- ブラウザーの Cookie に異常がないか。シークレットウィンドウで試してください。
- 監査ログにログイン失敗のスロットリングがないか。

### `admin` のパスワードを忘れた場合

`rbac:write` 権限を持つ他の管理者アカウントがまだある場合は、**プラットフォーム権限 → ユーザー** でパスワードをリセットすることを優先してください。

使用可能な管理者セッションがない場合は、サーバー上で組み込みの `admin` アカウントを緊急リセットできます。プロジェクトのルートディレクトリで実行します。

```bash
./run.sh --reset-admin-password
```

プロンプトに従って新しいパスワードを入力し、確認します。スクリプトは入力を非表示にし、bcrypt ハッシュを書き込みます。サービスが実行中の場合は、完了後にサービスを再起動して、既存のログインセッションを無効にしてください。

`run.sh` を使用できない場合は、次のコマンドを手動で実行し、プロンプトに従って新しいパスワードを入力して確認することもできます。

```bash
HASH=$(htpasswd -nBC 10 '' | cut -d: -f2 | tr -d '\n') && sqlite3 data/conversations.db "UPDATE rbac_users SET password_hash='$HASH', updated_at=CURRENT_TIMESTAMP WHERE id='admin' AND username='admin' AND is_builtin=1; SELECT changes();"
```

`1` が出力されれば変更は成功です。このコマンドには `sqlite3` と `htpasswd` が必要です。`config.yaml` の `database.path` がデフォルト値でない場合は、`data/conversations.db` を置き換えてください。パスワード入力は表示されず、Shell の履歴にも書き込まれません。

## モデルが応答しない

確認事項：

- 現在の会話で選択している AI チャネルが存在するか。空の場合は `ai.default_channel` が使用されます。
- `ai.channels.<id>.base_url` に `/v1` などの正しいパスが含まれているか。
- `ai.channels.<id>.api_key` が有効か。
- `ai.channels.<id>.model` が存在するか。
- サービスプロバイダーが、現在のチャネルの `reasoning` フィールドをサポートしているか。

システム設定でモデルテストを使用できます。ゲートウェイが 400 を返す場合は、まず次を試してください。

```yaml
ai:
  channels:
    your-channel:
      reasoning:
        mode: off
```

## ストリーミング出力が途切れる

よくある原因：

- リバースプロキシが SSE をバッファリングしている。
- モデルゲートウェイのタイムアウト。
- ブラウザーのネットワーク切断。
- コンテキストが大きすぎる。

Nginx では次が必要です。

```nginx
proxy_buffering off;
proxy_http_version 1.1;
```

## ツールの実行に失敗する

確認事項：

- ツールのコマンドが PATH 上にインストールされているか。
- `tools/*.yaml` のパラメーター schema が正しいか。
- HITL に拒否されていないか。
- `agent.tool_timeout_minutes` を超過していないか。
- Shell の長時間無出力により `shell_no_output_timeout_seconds` が発動していないか。

ツール設定は `tools/README.md` を参照してください。

## MCP に接続できない

組み込み MCP：

- `mcp.enabled` を確認します。
- `mcp.port` を確認します。
- `auth_header` と `auth_header_value` を確認します。

外部 MCP：

- stdio：コマンドパス、作業ディレクトリ、環境変数を確認します。
- HTTP/SSE：URL、認証、ネットワーク疎通を確認します。
- `/api/external-mcp/stats` を確認します。

## ナレッジベースが使えない

確認事項：

- `knowledge.enabled: true`。
- embedding の設定が正しいか。
- スキャンとインデックスの再構築が済んでいるか。
- `data/knowledge.db` に書き込めるか。
- 埋め込みサービスが 429 を返したりタイムアウトしたりしていないか。

インデックス作成が大量に失敗する場合は、次の値を下げてください。

```yaml
knowledge:
  indexing:
    batch_size: 5
    rate_limit_delay_ms: 600
```

## ボットが返信しない

確認事項：

- 対応するプラットフォームの `robots.<platform>.enabled`。
- プラットフォームのコールバック URL が `/api/robot/...` を指しているか。
- Token、secret、verify_token が一致しているか。
- サーバーにプラットフォームからアクセスできるか。
- グループチャットでボットへの @ メンションが必要か。

詳細な手順は [ボットの使い方](robot.md) を参照してください。

## C2 リスナーの起動に失敗する

確認事項：

- `c2.enabled`。
- ポートが使用されていないか。
- ファイアウォールまたはセキュリティグループ。
- 低いポートにバインドするのに管理者権限が必要ではないか。

C2 を無効にした後、`/api/c2/*` が 503 を返すのは想定どおりの動作です。

## WebShell のコマンド出力が文字化けする

対処：

- 対象システムのエンコーディングを確認します。
- より短いコマンドを試します。
- base64 で出力をラップします。
- Windows ターゲットではコードページを確認します。

## データベースのロックまたは書き込み失敗

確認事項：

- `data/` に書き込めるか。
- 複数のインスタンスが同じ SQLite ファイルを共有していないか。
- ディスクが満杯ではないか。
- WAL/SHM ファイルを誤ってコピーしていないか。

本番環境では、複数のプロセスが同時に同じ SQLite データベースへ書き込まないようにしてください。

## フロントエンドページの異常

確認事項：

- ブラウザーコンソールのエラー。
- 静的リソースが正常に読み込まれているか。
- フロントエンドを変更した後にキャッシュを更新したか。
- i18n key が欠落していないか。

API に異常がある場合は、`/api-docs` を開いてリクエストボディと照合してください。

## 診断の順序

問題が発生したときは、すぐに設定を変更せず、まず階層を特定してください。

1. プロセス：サービスがまだ稼働しているか、ログに panic がないか。
2. ネットワーク：ポート、HTTPS、リバースプロキシ、ブラウザーコンソール。
3. 認証：`/api/auth/validate` が 200 を返すか。
4. 設定：`/api/config` を読み込めるか、適用後にエラーが出ないか。
5. モデル：モデルテストに通るか。
6. ツール：ツール一覧と個々の schema が正常か。
7. データベース：`data/` に書き込めるか、ロックがないか。
8. 業務モジュール：ナレッジベース、MCP、C2、WebShell について、それぞれ最小限の動作をテストします。

まず階層を特定してから、パラメーターを変更してください。そうしないと、プロキシの問題をモデルの問題と誤判定しやすくなります。

## 最小限の診断コマンド

```bash
# プロセスとポート
lsof -i :8080

# ローカルの HTTPS が通じるか
curl -k -I https://127.0.0.1:8080/

# 静的リソースが通じるか
curl -k -I https://127.0.0.1:8080/static/logo.png

# データベースファイルを確認
ls -lh data/
```

Nginx を経由している場合は、プロキシアドレスとオリジンアドレスをそれぞれテストして、問題がどの階層にあるかを確認してください。

## よくある誤判定

- 「モデルが壊れた」：実際は HITL が承認待ちで保留している。
- 「ツールが読み込まれていない」：実際は tool_search がほとんどのツールを隠している。
- 「ナレッジベースが効かない」：実際はインデックスが再構築されていないか、risk_type のフィルターが狭すぎる。
- 「C2 API が壊れた」：実際は `c2.enabled: false` で、503 が返るのは正常な保護動作。
- 「設定を保存したのに反映されない」：実際は待ち受けポート／TLS の変更に再起動が必要。
- 「ボットが返信しない」：実際はプラットフォーム側でコールバック URL や署名検証パラメーターが正しく設定されていない。

## 障害報告テンプレート

問題を報告する際は、次を添付することを推奨します。

```text
バージョン/コミット：
起動方法：
アクセス方法：http/https/リバースプロキシ：
関連する設定セクション：
再現手順：
期待される結果：
実際の結果：
サーバー側ログ：
ブラウザーコンソール：
関連する API レスポンス：
```

これらの情報があると、原因の特定は通常かなり速くなります。
