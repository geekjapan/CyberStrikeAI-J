# リリースプロセス

[English](../en-US/release-process.md) | [中文](../zh-CN/release-process.md)

本書は、メンテナーまたはデプロイ担当者が CyberStrikeAI をリリース、アップグレード、ロールバックするためのものです。

## バージョンの準備

リリース前のチェック：

- `README.md` と `README_CN.md` の機能説明が更新されているか。
- `docs/` に新機能のドキュメントが追加されているか。
- `config.example.yaml` のサンプルに、新しく追加された設定が含まれているか。
- OpenAPI に、新しく追加されたインターフェースが含まれているか。
- 中国語・英語の i18n が同期されているか。
- 高リスクな機能にセキュリティに関する説明があるか。

## テスト

少なくとも次を実行します。

```bash
go test ./internal/...
```

エントリーポイント、ビルド、またはコマンドを変更した場合：

```bash
go test ./cmd/...
bash scripts/build-pi-runtime.sh
go build -o cyberstrike-ai ./cmd/server
```

フロントエンドを変更した場合は、次を手動で検証します。

- ログイン。
- 会話のストリーミング出力。
- 設定の保存と適用。
- ツール一覧。
- 関連するページにコンソールエラーがないこと。

## ビルド

```bash
bash scripts/build-pi-runtime.sh
go build -o cyberstrike-ai ./cmd/server
```

リリースパッケージには、次を含めてください。

- `cyberstrike-ai`
- `web/static/`
- `config.example.yaml` のサンプル。
- `tools/`
- `roles/`
- `skills/`
- `agents/`
- `docs/`
- `README.md` / `README_CN.md`
- `LICENSE`

ローカルの `data/`、実際の `config.yaml` のシークレット、アップロードされた添付ファイル、ログを、公開のリリースパッケージに含めないでください。

## アップグレードのチェックリスト

アップグレード前：

- サービスを停止する。
- `config.yaml` をバックアップする。
- `data/` をバックアップする。
- カスタムの `tools/roles/skills/agents/knowledge_base` をバックアップする。
- 現在のバージョンと起動方法を記録する。

アップグレード後：

- サービスを起動する。
- ログインする。
- モデルをテストする。
- ツール一覧を確認する。
- ナレッジベースの状態を確認する。
- 外部 MCP を確認する。
- C2/WebShell が想定どおりに有効または無効になっているかを確認する。
- ログと監査を確認する。

## ロールバック

ロールバックのきっかけとなる主なケース：

- サービスが起動できない。
- データベースのマイグレーションが失敗した。
- コアとなる会話機能が利用できない。
- 高リスクな機能の動作が異常である。

ロールバックの手順：

1. 新バージョンを停止する。
2. 古いバイナリまたは古いコードを復元する。
3. アップグレード前の `config.yaml` を復元する。
4. アップグレード前の `data/` を復元する。
5. 古いバージョンを起動して検証する。

新バージョンがデータベースの構造を変更している場合は、バイナリを置き換えるだけでは不十分で、データベースのバックアップを復元する必要があります。

## Changelog の推奨事項

各バージョンで記録する内容：

- 新機能。
- 動作の変更。
- 設定の変更。
- データベースの変更。
- セキュリティ修正。
- 互換性に関する説明。
- アップグレード時の注意事項。

高リスクなモジュール（C2、WebShell、ターミナル、外部 MCP、HITL など）の変更は、個別に明示してください。

## リリースのリスク分類

| 変更 | リスク | 必須のテスト |
| --- | --- | --- |
| ドキュメント、画像 | 低 | リンクとレンダリング |
| フロントエンドのページ | 中 | ログイン、ページの状態、API エラー |
| Handler/API | 中 | OpenAPI、権限、エラーコード |
| 設定の構造 | 高 | 古い設定との互換性、ApplyConfig |
| データベースの構造 | 高 | 古い DB のマイグレーション、ロールバック方針 |
| Agent/MCP/HITL | 高 | ツール呼び出し、承認、ストリーミングの中断 |
| C2/WebShell/Terminal | 極めて高い | 認可された環境、監査、無効化スイッチ |

リリースノートでは、機能の項目を並べるだけでなく、リスクレベルごとにユーザーへ注意を促してください。

## 設定の互換性ポリシー

新しい設定フィールドを追加する場合は、次に従います。

- 省略時に安全なデフォルト値があること。
- 古い設定で起動できること。
- サンプルの `config.yaml` にコメントがあること。
- Web の設定ページが、未知のフィールドを誤って削除しないこと。
- ホットアプライと再起動の 2 つのパスをどちらも検証すること。

新しいフィールドがデフォルトで高リスクな機能を有効にする場合は、デフォルト値を再検討してください。

## データベース変更のポリシー

SQLite のマイグレーションでは、次を考慮する必要があります。

- ユーザーが、非常に古いバージョンから直接アップグレードする可能性がある。
- マイグレーションが中断された後、再度起動しても冪等であるか。
- 新しいフィールドが NULL を許容するか。
- インデックスの作成が、テーブルを長時間ロックしないか。
- データのバックフィルが必要か。

リリースノートには、「アップグレード前に data/ をバックアップすること」を必ず明記してください。

## Release の受け入れスクリプトの考え方

最小限の自動化：

```bash
go test ./internal/...
go test ./cmd/...
bash scripts/build-pi-runtime.sh
go build -o cyberstrike-ai ./cmd/server
```

手動のスモークテスト：

```text
ログイン -> モデルテスト -> 新規会話 -> ツール一覧 -> HITL -> ナレッジベース -> 外部 MCP -> C2 の無効化/有効化
```

高リスクなモジュールでは、ユニットテストだけで通過させるのではなく、認可された演習環境でのテストをもう 1 つ実施してください。
