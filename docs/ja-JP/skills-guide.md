# Skills ガイド

[English](../en-US/skills-guide.md) | [中文](../zh-CN/skills-guide.md)

Skills は、エージェントにオンデマンドで読み込める専門的な機能、手順の説明、テンプレート、参考資料を提供するためのものです。一回限りのタスク入力ではなく、安定した方法論を担うのに適しています。

## ディレクトリ構成

デフォルトのディレクトリ：

```yaml
skills_dir: skills
```

推奨される構成：

```text
skills/
  api-security-testing/
    SKILL.md
  ssrf-testing/
    SKILL.md
  cyberstrike-pi-demo/
    SKILL.md
    REFERENCE.md
    assets/
```

各 Skill には、少なくとも `SKILL.md` が必要です。

## SKILL.md

`SKILL.md` は YAML front matter を使用します。

```markdown
---
name: ssrf-testing
description: SSRF 脆弱性の識別、検証、バイパス、修正提案のフロー
---

# SSRF Testing

タスクがサーバーサイドリクエストフォージェリ、URL コールバック、クラウドメタデータへのアクセス、または内部ネットワークの探索に関わる場合に、このスキルを使用します。
```

`description` は重要です。エージェントはこれを基に、いつ読み込むかを判断します。

## 段階的開示

Pi Skills はオンデマンドの読み込みをサポートしています。設定：

```yaml
multi_agent:
  skills:
    disable: false
    filesystem_tools: true
    skill_tool_name: skill
```

エージェントには最初はスキルの名前と説明だけが見え、本当に必要になったときに `skill` を呼び出して詳細を読み取ります。これによりコンテキストの使用量を減らします。

## Skill にするのに適した内容

- ある種の脆弱性のテストフロー。
- セキュリティ監査のチェックリスト。
- レポートのテンプレート。
- ツールの組み合わせ方法。
- 社内規約。
- よくある誤検知の判断。

適していないもの：

- 一時的なターゲット情報。
- API Key、パスワード、Cookie。
- 頻繁に変わるスキャン結果。
- 構造化されていない大量の生ログ。

## 付属ファイル

Skill には、`REFERENCE.md`、テンプレート、辞書、サンプルなどの付属ファイルを含めることができます。`SKILL.md` には、これらのファイルをいつ読み取るべきかを記載してください。

推奨事項：

- メインファイルは短く明確に保つ。
- 参考資料はトピックごとに分割する。
- 大きなファイルは必要な場合にのみ読み取る。

## ロールとのバインド

ロールはエージェントに特定の種類の Skill を使うよう促すことができます。また、Skill も、ページでの管理を通じてロールとのバインド関係を持てます。推奨事項：

- 汎用的なスキルはバインドせず、説明に基づいて自動的にトリガーされるようにする。
- 高リスクなスキルは専用のロールにバインドする。
- 同種のスキルで説明が過度に重複しないようにする。

## 開発上の推奨事項

Skill の内容構成：

1. トリガーとなるシーン。
2. 目標と境界。
3. 操作手順。
4. ツールの提案。
5. 出力形式。
6. リスクと禁止事項。
7. 参考資料。

人が読むだけでなく、エージェントが実行できる書き方にしてください。

## トラブルシューティング

Skill が使われない：

- `description` が狭すぎる、または曖昧すぎる。
- タスクにトリガーとなるキーワードがない。
- `multi_agent.skills.disable: true`。
- Skill ファイルの front matter の形式が誤っている。

Skill の読み取りが多すぎる：

- 付属ファイルを分割する。
- `SKILL.md` に「X が必要な場合にのみ Y を読み取る」と明記する。
- 重複した内容を削除する。

## Skill 設計の深い領域

Skill の核心的な価値は、「エージェントに一つの概念を知らせる」ことではなく、正しいタイミングで実行可能な手順一式をエージェントに渡すことです。Skill を書く際は、トリガー条件と終了条件に特に注意してください。

推奨される構成：

```markdown
## When to use
トリガーとなるシーンを明確にする。

## Preconditions
ユーザーが提供すべき情報と、ターゲットが満たすべき条件。

## Procedure
手順に従って実行し、各ステップでツール、入力、判断基準を説明する。

## Stop conditions
どのような場合に停止するか、承認へエスカレーションするか、人手に引き継ぐか。

## Output
最終結果の形式。
```

## アンチパターン

| アンチパターン | 結果 | 改善方法 |
| --- | --- | --- |
| 説明が広すぎる：`セキュリティテスト用` | ほぼすべてのタスクでトリガーされる | 具体的な脆弱性、シーン、シグナルを書く |
| 内容が百科事典のよう | エージェントが次に何をすべきかわからない | フローと決定木に書き換える |
| 機密設定を Skill に書く | 漏えいと誤用 | 実行時の設定またはユーザー入力を使う |
| 一つの Skill にすべてを詰め込む | 読み取りコストが高く、再現が混乱する | 脆弱性/タスクごとに分割する |
| 停止条件がない | エージェントが範囲を拡大し続ける可能性がある | いつ停止するか、いつ承認を求めるかを明記する |

## Skill とナレッジベースの違い

- Skill：エージェントに進め方を示すもので、フローを重視します。
- ナレッジベース：ファクト、事例、参考情報を提供するもので、検索を重視します。

SSRF を例にすると：

- Skill には「SSRF のテスト方法、判定方法、停止するタイミング」を書きます。
- ナレッジベースには「クラウドベンダーの metadata アドレス、過去のバイパス手法、修正方法」を書きます。

## ローカルファイルツールのリスク

`filesystem_tools: true` は、読み書きと実行の機能を公開します。開発や自動化には非常に有用ですが、セキュリティ境界でもあります。本番環境では次を推奨します。

- `workspace_root_dir` と組み合わせて作業ディレクトリを制限する。
- 書き込みと実行の操作には HITL を使用する。
- `execute` をグローバルなホワイトリストに加えない。
- 認可された範囲外のファイルの読み書きを Skill の中で明確に禁止する。
