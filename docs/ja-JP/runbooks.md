# 運用 Runbooks

[English](../en-US/runbooks.md) | [中文](../zh-CN/runbooks.md)

Runbook は、「実際のタスクに直面したときに、そのとおりに実行する」手順チェックリストです。本書は、CyberStrikeAI で最もよくある運用およびセキュリティテストの操作を扱います。

## Runbook 1：本番インスタンスをゼロから利用可能にする

適用対象：社内ネットワークのチームまたは本番レッドチームプラットフォームの初回デプロイ。

ローカルまたは一時的な検証だけであれば、リポジトリ付属のスクリプトで起動することを優先します。

```bash
chmod +x run.sh && ./run.sh
```

動作を確認してから、systemd + リバースプロキシによる長期運用デプロイへ移行するかどうかを決めます。

### 事前確認

- 稼働ホストが資産管理に登録されている。
- アクセス経路が決まっている：社内ネットワーク、VPN、踏み台ホスト、またはリバースプロキシ。
- モデルの API Key と、使用が許可されたモデルがある。
- C2、WebShell、外部 MCP を有効にするかどうかが決まっている。

### 手順

1. ディレクトリを準備する：

```bash
mkdir -p /opt/CyberStrikeAI
```

2. バイナリとリソースディレクトリを配置する：

```text
cyberstrike-ai
web/
tools/
roles/
skills/
agents/
docs/
config.yaml
```

3. 主要な設定を変更する：

```yaml
auth:
  session_duration_hours: 12
server:
  host: 127.0.0.1
  port: 8080
  tls_enabled: false
audit:
  enabled: true
c2:
  enabled: false
```

4. リバースプロキシで HTTPS を設定し、接続元 IP を制限する。
5. systemd でプロセスを管理する。
6. Web にログインし、モデルをテストする。
7. ツール一覧と監査ログを確認する。
8. バックアップ方針を策定する。

### 受け入れ確認

- ログイン後、`/api/auth/validate` が成功を返す。
- モデルのテストが成功する。
- `tools/` が正常に読み込まれる。
- 監査ページでログインイベントを確認できる。
- C2 が不要な場合、アクセスすると無効状態が返る。

### ロールバック

次を復元します。

- 1 つ前のバージョンのバイナリ。
- 1 つ前のバージョンの `config.yaml`。
- アップグレード前の `data/`。

## Runbook 2：外部 MCP を接続する

適用対象：ローカルのツールサービス、Burp の補助サービス、資産照会サービスなどの接続。

### 事前確認

- MCP サービスが信頼できる。
- ファイルの読み取り、ファイルの書き込み、コマンドの実行、サードパーティのネットワークへのアクセスが可能かどうかを明確にしている。
- 接続方式を決めている：stdio、HTTP、SSE。

### 手順

1. 外部 MCP ページでサービスを追加する。
2. stdio の場合は、コマンド、引数、作業ディレクトリ、環境変数を入力する。
3. HTTP/SSE の場合は、URL と認証情報を入力する。
4. サービスを起動する。
5. `/api/external-mcp/stats` を確認する。
6. ツール一覧にツールが表示されているか確認する。
7. リスクの低いパラメーターでツールを 1 回実行する。
8. 高リスクのツールを、グローバルな承認不要のホワイトリストから除外する。

### 受け入れ確認

- MCP の状態が running である。
- ツールの schema が確認できる。
- エージェントが `tool_search` でツールを見つけられる。
- ツールの実行記録が監視ページに表示される。
- 設定の変更が監査ページに表示される。

### ロールバック

- MCP を停止する。
- 外部 MCP の設定を削除する。
- ロールとホワイトリストから、関連するツールを削除する。
- エージェントの現在のタスクが、古いコンテキストを保持していないか確認する。

## Runbook 3：ナレッジベースを有効化し、ヒット率をチューニングする

適用対象：社内のセキュリティ知識、脆弱性ハンドブック、テスト手法をエージェントに接続する場合。

### 手順

1. 設定を変更する：

```yaml
knowledge:
  enabled: true
  base_path: knowledge_base
  embedding:
    model: text-embedding-v4
  retrieval:
    top_k: 5
    similarity_threshold: 0.4
```

2. Markdown を `knowledge_base/` に置く。
3. Web のナレッジベースページでスキャンを実行する。
4. インデックスを再構築する。
5. 5 〜 10 個の固定テスト質問を用意する。
6. 検索を実行し、ヒット状況を記録する。
7. 結果に応じて、`threshold`、`top_k`、チャンクのパラメーター、文書の見出しを調整する。

### 受け入れ確認

- `index-status` でインデックス作成の完了が表示される。
- よくある質問が正しい文書にヒットする。
- エージェントが、不確かな場合にまずナレッジベースを照会する。
- 検索ログに、クエリとヒットした文書が表示される。

### よくあるロールバック

- `knowledge.enabled` を無効にする。
- 古い `data/knowledge.db` を復元する。
- `batch_size` を下げてから、再度インデックスを作成する。

## Runbook 4：認可された Web テストの標準フロー

適用対象：認可されたターゲットに対する Web セキュリティテスト。

### 手順

1. プロジェクトを作成し、認可範囲を記録する。
2. 新しい会話を作成し、プロジェクトに紐付ける。
3. 最小限のロールを選択する。例：「情報収集」または「Web アプリケーションスキャン」。
4. ターゲット、時間枠、禁止事項を明確にする。
5. まず読み取り専用の情報収集を実行する。
6. 手がかりを見つけたら、プロジェクトのファクトに書き込む。
7. 高リスクの検証リクエストには HITL を使用する。
8. 脆弱性を確認したら、脆弱性管理に書き込む。
9. 攻撃チェーンまたはレポート用の資料を生成する。
10. アップロードしたファイル、一時的な workspace、不要な実行記録を整理する。

### 受け入れ確認

- すべての脆弱性に、証拠、影響、再現手順、修正提案がある。
- 高リスクの操作に HITL の記録がある。
- プロジェクトのファクトからテスト経路を再現できる。
- レポートに無関係な機密データが含まれていない。

## Runbook 5：C2 演習終了後のクリーンアップ

適用対象：認可された演習で C2 を有効にした場合。

### 手順

1. すべての listener を停止する。
2. sessions を一覧表示し、まだオンラインの認可されたセッションがないことを確認する。
3. 必要な task の結果をエクスポートする。
4. payload を削除するか、管理されたアーカイブに移動する。
5. 不要な task、event、file を削除する。
6. C2 の操作記録を監査する。
7. 重要な結果をプロジェクトのファクトまたはレポートに書き込む。
8. プラットフォームが継続的に必要としない限り、`c2.enabled` を false に戻す。

### 受け入れ確認

- 稼働中の listener がない。
- 処理待ちの task がない。
- payload が公開ダウンロードできない状態になっている。
- 監査とレポートで、ライフサイクル全体を説明できる。

## Runbook 6：エージェントがツールを呼び出さない

調査の順序：

1. 現在のロールにそのツールが紐付けられているか。
2. ツールが `/api/config/tools` に表示されるか。
3. `tool_search` がそのツールを隠していないか。
4. ツールの説明が短すぎないか、名前が不明確ではないか。
5. HITL が保留になっていないか。
6. エージェントが要約/終了のフェーズにいないか。
7. マルチエージェントのサブエージェントに、独自のツール制限がないか。

対処方法：

- ツールをロールに追加する。
- `short_description` を最適化する。
- `tool_search_always_visible_tools` に追加する。
- プロンプトで、どのような場合に使うかを明記する。
- プロセスの詳細と監視記録を確認する。
