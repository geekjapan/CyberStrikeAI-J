# 内蔵 C2 の使い方

[English](../en-US/c2.md) | [中文](../zh-CN/c2.md)

内蔵 C2 は、許可された環境でのセッション管理、タスクの送信、payload の生成、結果の回収に使用します。使用しないときは無効にしておくことを推奨します。

```yaml
c2:
  enabled: false
```

## 機能構成

主なオブジェクト：

- Listener：リスナー。セッションの受け付けを担当します。
- Session：接続してきたセッション。
- Task：セッションに送信するタスク。
- Payload：生成されたペイロードまたは one-liner。
- Profile：通信設定のテンプレート。
- Event：リスナー、セッション、タスクが生成するイベント。
- File：implant にダウンロードさせるファイル、またはタスク結果として回収したファイル。

Web API のプレフィックスは `/api/c2` です。C2 が無効のとき、API は `503 c2_disabled` を返します。

## リスナー

よく使う API：

- `GET /api/c2/listeners`
- `POST /api/c2/listeners`
- `POST /api/c2/listeners/:id/start`
- `POST /api/c2/listeners/:id/stop`
- `DELETE /api/c2/listeners/:id`

リスナーには分かりやすい名前を付け、演習プロジェクト、ネットワーク区画、許可範囲を明記することを推奨します。

## セッション

よく使う API：

- `GET /api/c2/sessions`
- `GET /api/c2/sessions/:id`
- `PUT /api/c2/sessions/:id/sleep`
- `DELETE /api/c2/sessions/:id`

`sleep` はセッションのポーリング間隔を調整します。間隔が短いほど操作はリアルタイムに近づきますが、通信量と露出面は増えます。

## タスク

よく使う API：

- `GET /api/c2/tasks`
- `POST /api/c2/tasks`
- `POST /api/c2/sessions/:id/tasks`
- `POST /api/c2/tasks/:id/cancel`
- `GET /api/c2/tasks/:id/wait`
- `GET /api/c2/tasks/:id/result-file`

タスクは許可されたターゲットと一致させてください。高リスクのタスクは HITL を経由させ、監査ログに操作の痕跡を残すことを推奨します。

## Payload

よく使う API：

- `POST /api/c2/payloads/oneliner`
- `POST /api/c2/payloads/build`
- `GET /api/c2/payloads/:id/download`

生成前に確認すること：

- コールバックアドレスが正しいか。
- プラットフォームとアーキテクチャが一致しているか。
- プロキシ、sleep、profile が必要か。
- ファイルを許可された環境にのみ配布するか。

## ファイル

よく使う API：

- `POST /api/c2/files/upload`
- `GET /api/c2/files`
- `GET /api/c2/tasks/:id/result-file`

アップロードしたファイルは implant がダウンロードできます。結果ファイルには機密情報が含まれる可能性があるため、プロジェクトの機密区分に従って保存し、クリーンアップしてください。

## MCP ツール

C2 を有効にすると、関連する MCP ツールが登録され、エージェントがリスナー、セッション、タスク、payload などを管理できるようになります。推奨事項：

- C2 ツールをグローバルの承認不要ホワイトリストに追加しない。
- ロールのプロンプトでプロジェクト、ターゲット、タスクの種類を制限する。
- コマンドの実行、ファイルのアップロード、payload の生成の各ステップで人による承認を有効にする。

## セキュリティ上の推奨事項

- 許可された環境でのみ有効にする。
- 管理用 Web をインターネットに公開しない。
- Listener の公開ポートと Web 管理ポートを分離する。
- セッション、タスク、payload、イベントを定期的にクリーンアップする。
- 演習の終了後はリスナーを停止し、不要な payload を削除する。
- 必要な監査証拠は残すが、機密性の高い出力を長期間保存しない。

## トラブルシューティング

リスナーを起動できない：

- ポートが使用中である。
- 権限が不足している。小さい番号のポートには追加の権限が必要です。
- ファイアウォールまたはセキュリティグループで許可されていない。

セッションが接続してこない：

- payload のコールバックアドレスが誤っている。
- ターゲットからリスナーに到達できない。
- TLS/Profile が一致していない。
- セキュリティ製品にブロックされている。

タスクの結果が返ってこない：

- セッションの sleep が長い。
- セッションがオフラインになっている。
- コマンドがターゲット側で停止している。
- 結果が大きすぎるため、結果ファイルとしてダウンロードする必要がある。

## ライフサイクルの視点

C2 の正しい使い方は「listener を作成してコマンドを送る」ことではなく、次のライフサイクルに沿うことです。

1. 許可の確認：プロジェクト、ターゲット、時間枠、許可された操作。
2. Profile の設計：通信方式、sleep、コールバックアドレス、ファイルチャネル。
3. Listener の起動：ポート、ネットワーク経路、ログを確認する。
4. Payload の生成：hash、用途、配布方法を記録する。
5. Session の接続：ターゲットの識別情報、権限、環境を確認する。
6. Task の送信：許可されたターゲットと一致するタスクのみを実行する。
7. 結果のアーカイブ：必要な出力をプロジェクトのファクトまたはレポートに記録する。
8. クリーンアップ：listener を停止し、payload を削除し、session/task/event をクリーンアップする。

最初の 2 ステップを省略すると、以降のすべての操作が監査できなくなります。

## タスクの分類

| レベル | 例 | 承認の推奨 |
| --- | --- | --- |
| L1 読み取り専用の識別 | `whoami`、ホスト名、カレントディレクトリ | 監査エージェントによる許可が可能 |
| L2 環境の列挙 | ネットワークインターフェース、プロセス、ユーザーグループ | 人による確認または厳格な監査を推奨 |
| L3 ファイルアクセス | 設定の読み取り、結果ファイルのダウンロード | 人がターゲットとパスを確認 |
| L4 変更を伴う実行 | ファイルのアップロード、sleep の変更、スクリプトの実行 | 人による承認 |
| L5 永続化/横展開/破壊 | 自動起動、認証情報、削除、暗号化、拡散 | 明確な許可がない限りデフォルトで拒否 |

この分類を HITL のプロンプトに書き込むほうが、単に「危険なら拒否」とするよりも運用しやすくなります。

## イベントの振り返り

1 回の C2 操作の振り返りでは、少なくとも次の問いに答えられる必要があります。

- どの listener がどの session を受け付けたか。
- payload は誰がいつ生成したか。
- session はどの許可されたターゲットに属するか。
- どの task を送信したか。
- task の出力をレポートまたはプロジェクトのファクトに記録したか。
- listener を停止し、payload をクリーンアップしたか。

これらに答えられない場合、C2 のプロセス管理がまだ一貫した形で完結していないことを意味します。
