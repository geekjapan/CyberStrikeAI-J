# 開発者ガイド

[English](../en-US/developer-guide.md)

本書は二次開発者向けに、プロジェクト構成、起動方法、主な拡張ポイント、開発上の作法を説明します。

## プロジェクト構成

```text
cmd/server/              Web サービスのエントリーポイント
internal/app/            アプリケーションの組み立て、ルート登録、MCP ツール登録
internal/handler/        HTTP Handler
internal/database/       SQLite データアクセス
internal/security/       認証、レート制限、Shell 実行
internal/mcp/            MCP Server、外部 MCP 管理
internal/multiagent/     Pi シングルエージェント、マルチエージェント、ミドルウェア
internal/workflow/       ワークフローランタイム
internal/knowledge/      ナレッジベースのインデックス作成と検索
internal/c2/             内蔵 C2
internal/project/        プロジェクトファクトのブラックボード
web/static/              フロントエンドの JS/CSS/リソース
web/frontend/            React + Semi Design のソース
tools/                   コマンドツール YAML
roles/                   ロール YAML
agents/                  マルチエージェントの Markdown 定義
skills/                  Agent Skills
docs/                    プロジェクトドキュメント
```

## 開発環境の起動

```bash
go run ./cmd/server --config config.yaml
```

フロントエンドのソースは `web/frontend/` にあります。`npm ci --prefix web/frontend` で依存関係をインストールし、`npm run --prefix web/frontend build` でビルドしてから、ページを再読み込みして動作を確認します。

## ルーティング

ルーティングは `internal/app/app.go` の `registerRoutes` に集約されています。業務 API を新規に追加する場合、通常は次の作業が必要です。

1. `internal/handler/` に Handler を追加する。
2. `internal/database/` に必要なデータアクセスを追加する。
3. `internal/app/app.go` で構築し、ルートを登録する。
4. 外部向けドキュメントが必要な場合は、`internal/handler/openapi.go` を更新する。
5. フロントエンドから呼び出す場合は、`web/frontend/src/pages/` を更新する。

## ワンクリックアップデート：インストールディレクトリに自身のソースコードを更新させる

デプロイ現場の日常は、「自分の fork が数十コミット進んだ → このインストールに取り込む → 再コンパイル → バイナリを入れ替える → 再起動」という流れです。
従来この作業には `upgrade.sh` しかなく、しかもそこには他人のリポジトリがハードコードされていました。fork を運用する人にとって「アップグレード」は「他人のコードで自分のコードを上書きすること」と同義だったのです。
現在この機能はプラットフォーム自体に組み込まれており（`internal/update`）、ページ、REST、CLI の 3 つの入口が同一の実装を共有しています。
そのため、各入口が示す拒否理由が食い違うことはありません。

### 3 つの入口

| 入口 | 使い方 |
|---|---|
| コンソール | 「システム設定 → ワンクリックアップデート」（旧ディープリンク `#system-update` も引き続き利用可能）。「今すぐ更新」でタスクを開始し、進捗をポーリングします。自動切り替えに対応したインストールでは、ビルド成功後にデフォルトで新しいバイナリへ切り替わり、サービス復旧後にページが自動的に更新されます。ロールバックボタンもあります |
| REST | `GET /api/system/update`（ディスクの現状を返す。ネットワーク接続なし）、`POST /api/system/update/check`（fetch 後に差分を報告）、`POST /api/system/update/apply`（`202` で `job_id` を返し、`GET /api/system/update/job` でポーリング）、`POST /api/system/update/rollback` |
| CLI | `./cyberstrike-ai -check-update`、`./cyberstrike-ai -update`、`./cyberstrike-ai -update-rollback`。インストールディレクトリは `--config` のあるディレクトリで、`--config` を指定しない場合はカレントディレクトリです |

権限は `update:read`（GET）と `update:apply`（4 つの書き込み API）です。`update:apply` はさらに、セッションが global（`all` scope）であることを要求します。
1 台のマシンにソースコードは 1 つしかなく、`assigned` / `own` scope のアカウントが、他人が稼働中のコードを動かせてはならないためです。

### コードの取得元

**アップデート元リポジトリ**から取得します。これは 1 つのリポジトリアドレスで、デフォルトは公式リポジトリ `https://github.com/AIPentest/CyberStrikeAI.git` です。
更新はそのリポジトリ**自身のデフォルトブランチ**に追従します（ブランチを設定する必要はなく、main をハードコードすることもありません）。
そのため、何も設定していないインストールでも、「どこから更新するか」には常に明確な答えがあります。`upgrade.sh` は現在、この実装の薄いラッパーにすぎません。このディレクトリが git ワークツリーであれば、直接
`./cyberstrike-ai -update` を呼び出します。

### アップデート元の変更（config.yaml の update セクション）

アップデート元のフィールドはリポジトリアドレスの 1 つだけです。空欄の場合は公式リポジトリを指します。自分の二次開発版、ミラー（GitHub へのアクセスが不安定な場合）、あるいは他人のリポジトリに追従したい場合は、この 1 か所だけを変更します。

```yaml
update:
  repo: https://github.com/AIPentest/CyberStrikeAI.git  # リポジトリのアドレスを 1 つ指定。空欄/未記入 = 公式リポジトリ
```

コンソールの「ワンクリックアップデート → アップデート元」ブロックで、このアドレスを直接編集して保存できます（空欄で保存すると公式リポジトリに戻ります）。
サーバーは保存時にアドレスを検証します。許可されるのは https/http/ssh/git/file:// とローカルの絶対パスのみです。git の `ext::` トランスポートはコマンドを実行するため、一律に拒否します。

### 非 git インストールの取り込み（展開・パッケージ版のインストール）

当初から Release パッケージを展開してインストールし、ディレクトリに `.git` がない場合は、同じページで「プレビューして接続」を実行できます（設定がなくてもデフォルトの公式リポジトリを使えます）。
プレビューは一時リポジトリで fetch を行い、まず**対象バージョンに置き換えられるローカルファイル**と**保持される運用者のコンテンツ**を一覧表示します。確認後、ディレクトリは git ワークツリーとして取り込まれ
（`git init` + origin の追加 + 対象ブランチの展開）、置き換えられたファイルはすべて
`.update-backup/<一意なバックアップディレクトリ>/overwritten/` に退避されます。運用者のコンテンツはこれまでどおり先に退避してから戻され、その後バイナリが再コンパイルされます。
取り込み後は通常のインストールとなり、ワンクリックアップデートもロールバックも利用できます。ただし、取り込み前には git 履歴がないため、「取り込み」自体にはロールバック可能な直前のコミットがありません。最初のロールバックポイントは、取り込み後の最初の更新で作成されます。

### バージョン番号はコードに追従する

リポジトリ内の `config.example.yaml` には、このコードに対応するリリースバージョンが記載されています（上流が release コミットと同時に変更します）。一方、あなたの
`config.yaml` は運用データであり、どの更新でも触れられることはありません。そのため、更新はマージ完了後に、新しいコードのバージョン番号を
`config.yaml` の `version` フィールドに書き戻します（この 1 行だけを変更し、一時ファイル + アトミックな置換で行います。進捗には「バージョン番号を新しいコードに合わせて
更新しました：v1.7.20 → v1.7.21」という行が出ます）。再起動後は、ページヘッダーのバージョンバッジも静的リソースの `?v=` もコードと一致します。これにより、アップグレード後はフロントエンドのキャッシュも
自動的に無効化されます。ロールバックではバージョン番号も一緒に元に戻ります（その間に誰も手で変更していない場合に限ります）。展開版インストールの「取り込み」時にも同様に 1 回同期します。
`version` の記述が行単位で置換できない形式（JSON の 1 行表記、複数行スカラーなど）の場合、書き込みは安全にスキップされて通知され、開けない
設定ファイルが生成されることはありません。読み取りは YAML パースを通し（`version` / `"version"` / `'version'` の 3 種類の書き方を認識します）、書き込み時の行マッチングも同じ基準です。

### 4 つの拒否シナリオ

| シナリオ | reason | 意味と対処 |
|---|---|---|
| **製品ソースコード**をローカルで変更している（protected リストにないパス） | `local_source_edits` | ワンクリックアップデートは「ダウンロード」であり、「競合の解決方法を代わりに決める」ものではありません。ファイルが名指しされるので、コミットまたは元に戻してから再試行してください |
| ブランチがリモートと**分岐**している（ローカルが先行かつ遅行） | `diverged` | これはマージの判断事項です。ahead/behind の数値が示されるので、手動で対処してから再度実行してください |
| ローカルに Go ツールチェーンがない | `no_toolchain` | **ソースコードは更新されます**が、バイナリだけが入れ替わりません。未コンパイル分は `.update-build-pending` に記録され（状態では `buildPending`、ページでは通常どおり「ワンクリックアップデート」が使えます）、`go` をインストールしてからもう一度実行すれば、実際に補完コンパイルされます |
| このディレクトリが git ワークツリーではない | `not_a_repo`（状態では `installed: false`） | tarball でインストールしたディレクトリにはファストフォワード可能なリモートがないため、リリースパッケージの方式で更新してください |

`apply` は非同期のため、常に先に `202` を返します。上表の拒否は、ポーリングで取得する `job.failure`（`reason` / `message` / `items`）に現れます。
`rollback` は同期のため、拒否は直接ステータスコードに反映されます（`local_source_edits`、`diverged`、`no_state`、`moved_since_update`、
`no_binary` → 409、それ以外 → 400）。その他の失敗（`merge_failed`、`build_failed`、`swap_failed`）には git/go の生の出力が付きます。
コンパイルに失敗した場合、バイナリは元のバージョンのままですが、ソースコードはすでに移動し、状態ファイルも書き込み済みのため、ロールバックは引き続き可能です。

チェック、更新、取り込み、ロールバック、再起動は、インストールディレクトリのシステムファイルロック（`.update-lock`）を共有します。
`update_busy` が返った場合は、別の操作が完了するまで待ってください。プロセス終了後はロックがシステムによって解放されるため、排他制御を回避する目的でロックファイルを削除しないでください。

### 運用者のコンテンツはどのように保持されるか

`roles/ skills/ tools/ agents/ knowledge_base/ data/ log/ venv/ config.yaml .env` は**運用者のコンテンツ**であり、
判定は `update.Protected` で行われます。マージの前に、今回の更新が**実際に書き込む**パスだけが
`.update-backup/<一意なバックアップディレクトリ>/` にコピーされてワークツリーから退避され（あなたが追加した、上流が触れていないディレクトリには一切手を付けません）、マージ後にそのまま戻されます。
こうして「コードは更新し、自分の作業は残す」が成立します。結果の `keptContent` は、保持されたファイルを 1 つずつ名指しします。黙って破棄されることは決してありません。
上流とあなたが同じファイルをどちらも変更していた場合、反映されるのはあなたのバージョンであり、そのことは結果に記載されます。
**ロールバックも同じルールに従います**。`reset --hard` は、保護対象ファイルに現存するローカルの変更を先に退避し、リセット後に戻します（更新前の変更も更新後の変更も対象で、
ローカルで削除したものは削除されたままです）。`keptContent` も同様に名指しします。ロールバックで取り消されるのはコードであり、あなたのコンテンツではありません。

### ロールバック

`./cyberstrike-ai -update-rollback` またはページのボタンを使います。`git reset --hard` でその更新前のコミットに戻り、
バイナリを入れ替えていた場合は `cyberstrike-ai.prev` が元の場所に戻され、その後 `.update-state.json` が削除されます。
コンパイルに失敗した更新ではバイナリを入れ替えたことがないため、そのロールバックではソースコードだけを戻します。ディスク上のバイナリは、もともと戻り先のコミットに属するものだからです。
次の場合、ロールバックは拒否されます。更新記録がない（`no_state`）、バイナリを戻す必要があるのに `cyberstrike-ai.prev` が残っていない（`no_binary`）、
記録内のコミットがこのリポジトリに存在しない（`bad_state`）、ディスク上のバイナリが記録内でそのコミットと対になっているものではない（`binary_changed`）、
**その更新以降に HEAD が動いている**（`moved_since_update`：ロールバックは更新前までしか戻すべきではなく、その後の作業をついでに消してはならない）、
そしてローカルのソースコード変更がある（`local_source_edits`）場合です。

ロールバックの開始前に `.update-rollback-pending.json` が書き込まれます。中断後に再度ロールバックを実行すると、復旧が継続されます。ページの
`rollbackPending` の表示中は、新しい更新が一時停止されます。復旧記録、バックアップディレクトリ、`.prev` は保持し、手動で削除しないでください。
記録内のバイナリのハッシュが現場のものと対応しない場合、上書きを拒否して現場を保持します。

### 新しいバイナリへの切り替え

macOS/Linux で、設定ファイルと同じディレクトリの `cyberstrike-ai` から起動している場合、「今すぐ更新」をクリックすると `restart: true` が直接送信され、再確認は不要です。
バイナリのビルドと入れ替えが成功した場合にのみ切り替えが行われます。サービスはまずアプリケーションリソースを閉じ、その後、同じ PID、起動引数、環境、作業ディレクトリで新しいバイナリを実行します。
サポート外の起動方法では自動切り替えは提供されず、REST が明示的に再起動を要求した場合は `400` を返します。REST でこのフィールドを渡さない場合と、CLI による更新では、ディスク上のファイルを入れ替えるだけです。

**反映待ちの状態は永続的で、後から再起動できます。** 状態 API は、「起動時に記録したバイナリの識別情報（サイズ + ナノ秒単位の mtime）」とディスク上の
現在値を比較します。更新、ロールバック、または CLI でバイナリを入れ替えたまま再起動していない場合、`needsRestart` が true になり、`binaryBuiltAt` にビルド時刻が入り、
コンソールの上部に常駐バナーと「今すぐ再起動」が表示されます（`POST /api/system/update/restart`。反映待ちのバージョンがない場合は
`409 nothing_pending`、実行中のタスクがある場合は `409`、サポート外の場合は `400`）。コンソールは `canRestart` に基づいて自動切り替えが可能かどうかを判断します。

**再起動後、ページは自動的に更新されます。** コンソールは 2 秒ごとにセッション検証 API を通じてサービスの起動マーカーを確認し、新しいマーカーを受け取った時点で初めてページを更新します。
セッションの引き継ぎに対応する 2 つのバージョン間で切り替える場合、有効なログインは元の有効期限を維持し、権限は新しいプロセスの RBAC ストアから再読み込みされます。旧バージョンから初めてアップグレードする際は、再ログインが必要になる場合があります。コンソールから離れると、確認は停止します。

## データベース

デフォルトは SQLite です。テーブルやフィールドを追加する場合は、次の点に従ってください。

- マイグレーションのロジックは、データベースの初期化処理または対応するモジュールのマイグレーション関数に置く。
- 後方互換性を保ち、既存の `data/conversations.db` を壊さないようにする。
- マイグレーションとコアクエリに対する単体テストを追加する。

## ツールの追加

コマンドツールは、`tools/*.yaml` で追加することを優先します。Go コードを変更する必要はありません。Go の組み込みツールが必要な場合は、次のようにします。

- 適切なモジュールで MCP Tool を登録する。
- 明確な `InputSchema` を定義する。
- タイムアウト、エラー、監査、HITL コンテキストを処理する。
- 高リスクの操作をデフォルトで承認不要にしない。

ツール YAML のルールは `tools/README.md` を参照してください。

## ロールの追加

ロールは `roles/*.yaml` で管理します。主なフィールドには、名前、説明、システムプロンプト、ツールリストがあります。ロールは最小ツールセットの原則に従い、専用ロールにすべてのツールをデフォルトで渡さないようにしてください。

## サブエージェントの追加

マルチエージェントのサブエージェントは `agents/*.md` に置きます。Front matter の例は次のとおりです。

```yaml
---
name: Vulnerability Triage
id: vulnerability-triage
description: 脆弱性の手がかりを検証し、深刻度を判定して、修正提案を整理する
tools:
  - nmap
  - nuclei
bind_role: Comprehensive Vulnerability Scanning
max_iterations: 200
---
```

本文がシステムプロンプトになります。メインエージェントには、固定のファイル名または `kind: orchestrator` を使用できます。

## Skill の追加

Skill は `skills/<name>/SKILL.md` に置きます。専門分野の機能、手順の説明、付属資料を提供するために使います。詳細は [Skills ガイド](skills-guide.md)を参照してください。

## フロントエンド開発

フロントエンドのコードは、機能ごとに `web/frontend/src/pages/` に分割されています。ページやモジュールを新規に追加する場合は、次の点に従ってください。

- `src/lib/http.js`、共有 UI コンポーネント、翻訳関数を再利用する。
- `web/static/i18n/en-US.json` と `ja-JP.json` を同期して更新する。
- 機密性の高いキーをフロントエンドに置かない。
- 高リスクのボタンには、確認と明確な状態フィードバックを付ける。

i18n の規約は[フロントエンド国際化方針](frontend-i18n.md)を参照してください。

## OpenAPI

`internal/handler/openapi.go` が組み込みの OpenAPI 出力を管理しています。公開 API を新規に追加したら、次の項目も合わせて補うことを推奨します。

- path
- method
- summary/description
- requestBody
- responses
- security

こうすることで、`/api-docs` に最新の API が反映されます。

## 開発の作法

- 既存のモジュール境界を優先して維持する。
- 大規模モデル、外部 API、ファイルシステム、Shell に関わる変更では、タイムアウトとエラー経路を必ず考慮する。
- 高リスクの機能は HITL に接続するか、少なくとも明確な監査を備える。
- コード変更後は、関連パッケージの単体テストを実行する。

## 業務モジュール新規追加のフルレシピ

Handler を追加するだけで済ませないでください。完全なモジュールでは、通常、次の点を検討する必要があります。

1. データモデル：SQLite のテーブルとマイグレーションが必要か。
2. Handler：HTTP パラメーター、エラーコード、ページネーション、フィルター。
3. Audit：管理操作を監査する必要があるか。
4. Monitor：長時間のタスクを実行する場合、実行状態を記録する必要があるか。
5. MCP：エージェントに公開する必要があるか。
6. HITL：MCP ツールに承認の境界があるか。
7. OpenAPI：`/api/openapi/spec` を更新する必要があるか。
8. Frontend：i18n、状態、空状態、エラー表示が必要か。
9. Tests：データベース、handler、境界条件。
10. Docs：設定、使い方、トラブルシューティング、セキュリティへの影響。

これらのどれかを欠くと、後から「ユーザーが理解できない」「エージェントが誤って呼び出す」「API を誰も使えない」といった形で手戻りが発生しがちです。

## Handler のエラー設計

エラーレスポンスは次の形式を保つことを推奨します。

```json
{
  "error": "machine_readable_code",
  "message": "ユーザーに表示する説明"
}
```

Go の error 文字列だけを返さないでください。フロントエンドには安定したフィールドが、ユーザーには実行可能な助言が、ログには詳細なエラーが必要です。

## 長時間タスクの設計

スキャン、インデックス作成、バッチタスク、C2 などは、長時間実行される可能性があります。設計時には次の問いに答える必要があります。

- キャンセルできるか。
- 進捗を照会できるか。
- 失敗後に再試行できるか。
- 結果はどこに書き込まれるか。
- ページを再読み込みしても状態は残るか。
- HTTP リクエストをブロックしないか。

答えが「いいえ」の場合は、タスクテーブル、イベントストリーム、または監視モジュールへの接続を検討してください。

## テストの優先順位

テストを補う価値が最も高いのは、次の箇所です。

- 設定のホット適用。
- HITL の承認分岐。
- Shell のタイムアウトと出力なし。
- 外部 MCP の障害復旧。
- ナレッジベースのインデックス作成と、検索後の後処理。
- WebShell のエンコーディングとシステム識別。
- SQLite のマイグレーション互換性。

これらの箇所は、通常の getter/setter よりも、実際のユーザー障害が起きやすい場所です。

### 復旧証拠と MCP 編集時の起動/停止状態

セルフアップデートの復旧は、ファイルを書き換える前に、JSON のフィールド名/型、重複キー、コミットとハッシュの対応、および実際のバイナリファイルを検証します。旧バージョンのプレーンテキストの未コンパイルマーカーも引き続きサポートされますが、関連する State も検証を通過する必要があります。記録が不完全、矛盾している、または形式がサポート外の場合は、復旧を拒否し、ファイルと復旧証拠を保持します。エラーを回避するだけの目的でマーカーを削除せず、まずソースコードのコミット、現在のバイナリ、旧バイナリ/バックアップの対応を確認してください。

既存の外部 MCP を編集する際、起動/停止フィールドを省略すると、現在の有効/停止状態が維持されます。明示的な `disabled` または `external_mcp_enable` で起動/停止状態を変更でき、`disabled: true` が優先されます。新規作成した MCP はデフォルトで有効です。起動/停止ボタンは対応する disabled 状態も同時に永続化するため、編集やアプリの再起動によって、停止中のサービスがいつの間にか有効になることを防げます。
