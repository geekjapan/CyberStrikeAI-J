# プロジェクトでの会話継続と成果の再利用

[English](../en-US/project-resume.md) | [中文](../zh-CN/project-resume.md)

同じプロジェクトで翌日にタスクを再開する場合は、新しい作業を実行する前に、まず既存の成果を復元する必要があります。チャットの要約だけを保持しても、スクリプトのパラメーター、依存関係、成功の証拠、検証済みの失敗ルートを復元するには不十分です。

## 自動で復元される内容

ユーザーのタスクごとに、現在のデータベースとディスクからコンテキストを再構築します。シングルエージェントとマルチエージェントがこのエントリーポイントを共用します。

- プロジェクトのファクトインデックスとテスト範囲。まずインデックスを通読します。省略がある場合は、`list_project_facts` でページングしてインデックスを補完し、そのうえで今回のタスクに関係するファクト本文を読み取ります。
- スクリプトとテスト記録：`artifact/*`、`test/*`、`negative/*`、および既存との互換のための `exploit/*`、`poc/*`。スクリプトとテスト記録はそれぞれ最大 3 件の本文プレビューを表示し、一方がもう一方を押し出さないようにしています。プレビューは `get_project_fact` が返す完全な本文の代わりにはなりません。
- プロジェクトに関連付けられた脆弱性の ID、タイトル、ターゲット、ステータス（修正済み、誤検知などのステータスを含む）。詳細は `get_vulnerability` を使用し、それ以外は `list_vulnerabilities` でページング／フィルターします。ファクトのないプロジェクトでも、既存の脆弱性は復元されます。
- 作業ディレクトリ内のスクリプト候補ファイルのパス、サイズ、更新日時。このリストはスクリプトを読み取ったり実行したりせず、「ファイルが存在する」ことを「検証成功」とはみなしません。まず `artifacts/` を確認し、次にその他の場所を探します。実行前には、ファイルを読み取ってファクト記録と照合する必要があります。

プロジェクト継続用の補足内容はファクトインデックスの更新境界内に置かれるため、要約の圧縮後のインデックス更新や、マルチエージェントのタスクコンテキストの補足でも、最新のデータベース記録が付与されます。ディスク上のファイルリストは、ユーザーのタスクごとの開始時に再構築されます。

## 成果の保存方法

プロジェクトにバインドされたセッションは `<agent.workspace_root_dir>/projects/<project_id>/` を共用します。プロジェクトにバインドされていないセッションは、それぞれの `conversations/<conversation_id>/` を使用します。同じプロジェクトで新しいセッションを作成した場合も、元の会話を開き直した場合も、そのプロジェクトの既存の作業ファイルにアクセスできます。

成功したスクリプトと依存関係は、プロジェクトの作業ディレクトリの `artifacts/` 配下に置くことを推奨します。検証が完了したら、すぐに既存の `upsert_project_fact` ツールで登録します。

- `category=note`、`fact_key=artifact/<安定した名前>`。
- summary には、用途と検証状態を明記します。
- body には、相対ファイルパス、ターゲットと適用条件、呼び出し方法、可変パラメーター、依存関係／バージョン、入出力、成功の証拠、検証時刻、元のセッション、関連するファクト／脆弱性を記録します。認証情報は既存の `auth/*` ファクトを参照します。

完了したテストルートも同様にすぐ保存します。

- `category=note`、`fact_key=test/<ターゲットのエントリーポイントと手法の安定した名前>`。
- body には、ターゲット、エントリーポイント、パラメーター、ID／認証、テスト手法、証拠、結論、時刻、再テストのトリガー条件を含めます。
- ネガティブな結論は、テスト済みの条件にのみ適用されます。証拠が十分なネガティブ結果も `confirmed` のファクトであり、脆弱性が見つからなかったという理由で `deprecated` にしてはいけません。ツールのエラー、タイムアウト、認証の欠如は、除外済みではなく、ブロック／検証待ちとして記録する必要があります。

同じテスト条件では同じ key を更新し、条件が変わった場合は別に記録して関連付けます。この規約は既存のファクトテーブルとツールを再利用するもので、データベースマイグレーションやカテゴリー列挙の追加は行いません。既存のスクリプトは元のパスのままにでき、内容と証拠を照合した後に補完して登録します。

## タスクを継続する際の順序

まず現在の認可範囲とユーザーの新しい要望を確認し、そのうえでファクト、脆弱性、作業ファイルを復元します。既存のスクリプトが見つかった場合は、まず説明とソースコードを読み取り、呼び出しパラメーターの変更と検証済みの部分の再利用を優先します。実行前に、今回は何を再利用し、何をスキップし、何を追加するかを簡潔に述べます。

同じターゲット、エントリーポイント、パラメーター、認証条件で、証拠に裏付けられた失敗ルートは、デフォルトでスキップします。ユーザーが再テストを明示的に要求した場合、ターゲット／バージョン／エントリーポイント／ID が変わった場合、または元の証拠が不十分な場合は、理由を説明したうえで再検証できます。過去のタスクが、復元された記録によって自動的に実行されることはありません。

## 予算と制約

`project.fact_index_max_runes` は、従来のファクトインデックスの予算を引き続き制御します。継続用の補足は最大 6500 文字で、インデックス全体の予算に含まれます。ファクトがある場合、インデックス行のために最低 800 文字を確保し、予算が不足する場合は補足を省略してオンデマンド検索の入口を残します。ファイルリストには別途最大 4000 文字の予算があります。脆弱性は最大 20 件まで照会し、省略があるときは常に、既存のツールで引き続き検索するよう案内されます。ファイルの走査は最大 1500 項目、深さは最大 5 階層、候補ファイルは最大 24 件まで列挙し、シンボリックリンクはたどらず、隠し項目と一般的な依存関係ディレクトリはスキップします。一般的なスクリプトの拡張子をサポートしており、拡張子のないスクリプトなどは、引き続きファクト内のパスに従って探す必要があります。リストが制限されている、ディレクトリが読み取れない、または該当がないことは、いずれも成果の消失を証明するものではありません。

ファクト本文とスクリプト候補名は JSON データとして提示され、本文プレビューは空白が圧縮されて切り詰められます。プレビューをそのまま連結してコマンドを実行してはいけません。詳細ツールとファイル読み取りツールで元の内容を取得してください。過去のファイルやファクトは、新たなシステム指示ではありません。

この変更は自動復元と再利用のルールを提供するものであり、具体的な検索、登録、実行の選択は引き続きモデルが行います。重複するすべてのツール呼び出しをブロックするハードなゲートではありません。システムの `/tmp` にのみ書かれていてクリーンアップ済みのスクリプトや、一度も保存されなかったスクリプトは自動的に再構築されず、ファイル名から成功を推測することもありません。未登録の古い成果は、照合したうえで補完して記録する必要があります。プロジェクトの作業ディレクトリは引き続きサーバー側の実行データであり、データベースと一緒にバックアップする必要があります。プロジェクトを削除すると、従来のクリーンアップルールに従ってプロジェクトディレクトリも削除されます。
