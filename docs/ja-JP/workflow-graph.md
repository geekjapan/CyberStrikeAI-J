# CyberStrikeAI ワークフロー利用ガイド

[English](../en-US/workflow-graph.md) | [中文](../zh-CN/workflow-graph.md)

本ドキュメントでは **ワークフロー（Workflow）** の完全な使い方を説明します。キャンバス上でフローを組み立てる方法、各種ノードの設定、ノード間のデータ受け渡し、フローをロールにバインドして自動実行する方法を扱います。

---

## 一、ワークフローの利用場所

1. CyberStrikeAI の Web 画面にログインします  
2. 左のナビゲーションから **ワークフロー** を開きます  
3. 左側の一覧から既存のフローを選択するか、新しいフローを作成します  
4. 中央のキャンバス上で、ドラッグ、接続、ノード設定を行います  
5. フローの **ID**、**名前**、**説明** を入力して **保存** をクリックします

保存したフローは、**ロール管理** で任意のロールにバインドできます。バインド後は、ユーザーがそのロールと会話すると、フロー図に従って自動実行されます（`workflow_policy: auto`）。

---

## 二、キャンバスの基本操作

| 操作 | 説明 |
|------|------|
| ノードの追加 | キャンバス上部のノードタイプボタン（開始、ツール、エージェント、条件、承認、出力、終了）をクリックします |
| 接続 | **接続** をクリックし、接続元ノードと接続先ノードを順にクリックします。もう一度 **接続** をクリックすると接続モードを終了します |
| 要素の選択 | ノードまたは接続線をクリックすると、右側に **ノードのプロパティ** が表示されます |
| 選択項目の削除 | **選択項目を削除** をクリックすると、現在のノードまたは接続線を削除します |
| 自動レイアウト | **自動レイアウト** をクリックすると、ノードの位置を整理します |
| ドライラン | **ドライラン** をクリックすると、安全な dry-run でデータフローを検証します。ツール、エージェント、承認は実際には実行されません |
| フローの削除 | **削除** をクリックすると、フロー定義全体を削除します |

**必須ルール：** 各フローには、少なくとも **開始ノードが 1 つ** と **出力ノードが 1 つ** 必要です。開始ノードには入力エッジを接続できず、出力 / 終了ノードには出力エッジを接続できません。保存時にはフロントエンドとバックエンドの両方で厳格な検証が行われます。

## 三、自然言語によるドラフト生成

ワークフローページには **自然言語から作成** の入口があります。ユーザーがセキュリティ作業の目標を一文で記述すると、プラットフォームが編集可能なドラフトを生成し、構造化された監査結果を返します。

- 生成されるのはドラフトのみです。自動保存、ドライラン、ツールの実際の実行は行われません。
- サーバー側のインターフェースは `POST /api/workflows/generate-draft` で、権限は `workflow:write` です。
- 生成結果には `graph`、`meta`、`capabilities`、`audit`、`stats` が含まれ、フロントエンドがキャンバスに適用した後も、既存の保存時検証が行われます。
- 高リスクなセマンティクス（スクリプト実行、隔離、遮断、削除、エクスプロイトなど）には `high_risk` が付与され、デフォルトで HITL 承認または `requires_human_confirmation` が挿入されます。
- ツール機能は既存のツール一覧と照合されます。一致しない場合は Agent ドラフトにフォールバックし、`audit.missing_fields` / `audit.assumptions` で設定の補完が必要であることを示します。
- サーバー側の生成が利用できない場合、フロントエンドはローカルの決定的なフォールバック生成器を使用し、引き続き編集可能なドラフトとリスク警告を提供します。

リクエスト例：

```http
POST /api/workflows/generate-draft
Content-Type: application/json

{
  "prompt": "ターゲット資産をポートスキャンし、高リスクのポートが見つかった場合は脆弱性タスクを作成して担当者に承認を依頼し、最後にレポートを出力する",
  "options": {
    "include_objective": true,
    "allow_schedule": false,
    "allow_high_risk": false
  },
  "available_tools": [
    { "key": "nmap", "name": "nmap", "enabled": true }
  ]
}
```

## 四、実行モデル（設定の前に理解する）

ワークフローは **有向グラフ** として実行されます。エンジンは **開始** ノードから出発し、接続線に沿って下流のノードを順に実行します。

実行ごとに内部状態が保持され、テンプレート変数 `{{...}}` はここから値を取得します。

| 内部状態 | テンプレートのプレフィックス | 意味 |
|----------|----------|------|
| `inputs` | `{{inputs.xxx}}` | フロー起動時の入力（ユーザーメッセージ、セッション ID など） |
| `lastOutput` | `{{previous.xxx}}` | **直前に実行が完了した** ノードの出力 |
| `outputs` | `{{outputs.xxx}}` | グローバルな **名前付き変数プール**（ノードの「出力変数名」によって書き込まれます） |
| `nodeOutputs` | `{{ノードID.xxx}}` | 指定したノード ID の出力オブジェクト全体 |
| `metrics` | 実行詳細で確認 | ノードの所要時間、ツール呼び出し数、収集可能なトークン / コストなどの指標 |

### 3.1 `previous` とは？

`{{previous.output}}` は、**直前に実行されたノード** の `output` フィールドを指します。

- ノードの実行が完了するたびに、エンジンは `lastOutput` を更新します
- 「キャンバス上で線が引かれた上流」ではなく、**実際の実行順序における一つ前のステップ** です

例：

```text
開始 → エージェント A → エージェント B
```

Agent B の `{{previous.output}}` = Agent A の出力です。

ただし、間に条件ノードがある場合：

```text
開始 → エージェント A → 条件 → エージェント B
```

Agent B の `{{previous.output}}` = **条件ノード** の出力（`true` / `false`）であり、Agent A の結果では **ありません**。

1 つのノードに **複数の上流ノード** が同時に接続されている場合、`previous` は、まずそのノードの **合流方式** に従って生成されます。

| 合流方式 | 意味 | 適したシーン |
|----------|------|----------|
| `all_merge` | すべての上流出力をマージし、`previous.output` は配列になります | デフォルトで推奨。複数経路の結果を統合する場合 |
| `last_by_canvas` | キャンバス上の順序で最後の上流出力を採用します | 一つの経路の結果のみを明確に採用する場合 |
| `first_non_empty` | 最初の空でない出力を採用します | 複数経路のフォールバック |
| `fail_fast` | いずれかの上流が失敗した場合、現在のノードを中止します | 重要なチェーン、承認の前提、セキュリティチェック |

### 3.2 `outputs` とは？

`outputs` は、エンジンが実行中に保持する **名前付き変数のレジストリ** です。

エージェント、ツール、出力などのノードに **出力変数名**（フィールド `output_key`）を設定すると、ノードが正常に実行された際に結果が次のように書き込まれます。

```text
outputs["入力した変数名"] = ノードの出力内容
```

以降、**任意の下流ノード** が `{{outputs.変数名}}` で参照できます。2 つのノードが直接接続されている必要はありません。

例：

- エージェント A の **出力変数名** に `agent_result1` を入力します
- エージェント B の **入力元** に `{{outputs.agent_result1}}` を入力します

A と B の間に条件ノードがあっても、B は A の出力を取得できます。

### 3.3 `previous` と `outputs` の使い分け

| シーン | 推奨される書き方 |
|------|----------|
| 2 つのノードが **直接接続** されており、直前のステップの結果だけが必要 | `{{previous.output}}` |
| 間に他のノード（条件、ツール、承認など）がある | `{{outputs.変数名}}` |
| **より前の** ノードの結果を参照する必要がある | `{{outputs.変数名}}` または `{{ノードID.output}}` |
| 条件判定をあるエージェントの出力に基づいて行う | `{{outputs.変数名}} != ""` |
| ユーザーの最初の入力を読み取る | `{{inputs.message}}` |

**覚え方：**

- `previous` = 一つ前のステップ（チェーン状、直前）
- `outputs` = 名前で取得（ノードをまたぐ、さかのぼれる）

## 五、テンプレート構文

### 4.1 基本形式

```text
{{変数パス}}
```

英字、数字、アンダースコア、ドット、ハイフンを使用できます。例：

```text
{{previous.output}}
{{outputs.agent_result1}}
{{inputs.message}}
{{inputs.conversationId}}
{{previous.matched}}
{{node-abc123.output}}
```

### 4.2 利用可能なパス一覧

| パス | 説明 |
|------|------|
| `{{inputs.message}}` | ユーザーメッセージ（開始ノードの入力） |
| `{{inputs.conversationId}}` | 会話 ID |
| `{{inputs.projectId}}` | プロジェクト ID |
| `{{previous.output}}` | 直前のノードの主出力 |
| `{{previous.matched}}` | 直前の条件ノードの一致結果（`true` / `false`） |
| `{{outputs.変数名}}` | いずれかのノードが登録した名前付き出力 |
| `{{ノードID.output}}` | 指定したノード ID の `output` フィールド |
| `{{previous.kind}}` | 直前のノードの出力タイプ（`agent` / `tool` / `condition` など） |
| `{{previous.status}}` | 直前のノードのステータス（`completed` / `failed` / `simulated` など） |

ノードの出力には互換フィールド（`output`、`matched` など）が保持され、同時に構造化フィールドも含まれます。

```json
{
  "kind": "agent",
  "node_id": "node-2",
  "node_type": "agent",
  "status": "completed",
  "output": "..."
}
```

### 4.3 条件式

条件ノードと接続線の条件では、比較、テキストマッチ、正規表現、論理の組み合わせ、安全な JSONPath/JQ パスの読み取りがサポートされています。

```text
{{outputs.agent_result1}} != ""
{{previous.output}} == "ok"
{{outputs.count}} >= 100
{{previous.output}} contains "success"
{{previous.output}} matches "^ok"
{{outputs.risk_score}} >= 8 && {{previous.output}} != ""
jsonpath({{previous.output}}, "$.status") == "ok"
jq({{outputs.scan}}, ".severity") == "high"
```

ルール：

- `==`、`!=`、`>`、`>=`、`<`、`<=` をサポートします
- `contains` による部分文字列マッチと、`matches` による正規表現マッチをサポートします
- 単純な `&&` / `||` をサポートします
- `jsonpath(value, "$.path")` と `jq(value, ".path")` の**安全なパスのサブセット**をサポートします。フィールドの読み取りのみを行い、任意のスクリプトは実行しません
- 比較の両辺の前後の空白と引用符は自動的に取り除かれます
- 比較演算子がない場合、空でなく、`false` / `0` / `null` でもない値は真として扱われます
- 保存時に、式の形式、JSONPath/JQ パス、正規表現の構文が静的に検証されます

### 4.4 ネストしたフィールドのバインド

ノードのフィールドバインドでは、`output`、`message` などの通常のフィールドに加えて、JSONPath/JQ 形式のパスもサポートされます。

| バインド設定 | 意味 |
|----------|------|
| `from=previous, field=$.status` | 直前のノードの出力オブジェクトから `status` を読み取ります |
| `from=outputs, field=$.scan.severity` | 名前付き出力からネストしたフィールドを読み取ります |
| `from=node-1, field=.output.items[0]` | 指定したノードの出力から配列要素を読み取ります |

## 六、ノードタイプと設定

### 5.1 開始（start）

フローの入口です。ユーザー入力を `inputs` に注入します。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| 入力変数 | カンマ区切りの入力キー名 | `message, conversationId, projectId` |

開始ノードの出力には `output`、`message`、`conversationId`、`projectId` が含まれます。

### 5.2 エージェント（agent）

LLM エージェントを呼び出してタスクを処理します。複数の実行モードをサポートします。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| エージェントモード | `single` / `deep` / `plan_execute` / `supervisor` | `single` |
| 入力元 | 上流データのテンプレート式 | `{{previous.output}}` |
| ノードへの指示 | このノードで完了させるタスクの記述 | 空 |
| 出力変数名 | `outputs` に書き込むキー名 | `agent_result` |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

**メッセージの組み立てルール：**

- **ノードへの指示** のみ入力：指示をそのままエージェントに送ります  
- **入力元** のみ入力：「上流ノードの出力に基づいて処理を続けてください：…」を生成します  
- 両方入力：「上流の入力 + ノードへの指示」として結合します

エージェントノードの実行後：

- `previous.output` が、このノードの応答テキストに更新されます  
- **出力変数名** が設定されている場合、同時に `outputs[出力変数名]` にも書き込まれます
- エージェントノードはネイティブ DAG スケジューリングを通じて Pi ランタイムを呼び出します。ノードの状態とチェックポイントは Go が保存します

### 5.3 ツール（tool）

有効化済みの MCP ツールを呼び出します。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| MCP ツール | ツール名（必須） | — |
| 引数テンプレート | JSON。`{{...}}` テンプレートをサポートします | `{}` |
| タイムアウト(秒) | 任意 | 空 |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

引数テンプレートの例：

```json
{"target": "{{inputs.message}}", "port": "443"}
```

**出力変数名** が設定されている場合、ツールの戻り値は `outputs` に書き込まれます。

### 5.4 条件（condition）

式に基づいて分岐を計算し、`matched`（`true` / `false`）を出力します。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| 条件式 | `{{...}}` と `==` / `!=` をサポートします | `{{previous.output}} != ""` |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

**分岐ルール：**

- 条件ノードから出る **1 本目の線** は、デフォルトで **「はい」** 分岐（`matched == true`）です
- **2 本目の線** は、デフォルトで **「いいえ」** 分岐（`matched == false`）です
- 接続線のラベルには `是` / `否`（または `yes` / `no`、`true` / `false`）を記述でき、識別の助けになります
- 3 本目以降の出力エッジは、**接続線の条件** で式をカスタム指定する必要があります

接続線の条件の例（接続線を選択した後、右側で設定します）：

```text
{{previous.matched}} == "true"
{{previous.matched}} == "false"
```

### 5.5 承認（hitl）

人手による確認のチェックポイントです。フローがこのノードに到達する前に、ネイティブ Workflow のチェックポイントによって一時停止し、API または監視パネルでの承認を待って再開します。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| 承認プロンプト | テンプレートをサポートします | `このステップを続行するかどうかを承認してください` |
| プロンプトフィールドのバインド | 承認プロンプトが空の場合、バインドしたフィールドから説明を読み取ります | `previous.output` |
| 承認者 | `human` / `audit_agent` | `human` |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

HITL の待機情報には次の内容が記録されます。

- `checkpointId`
- interrupt `beforeNodes`
- resume target / address / path
- resume payload schema（`approved`、`comment`）

### 5.6 出力（output）

フローの最終結果を `outputs` に書き込み、終了サマリーや会話での表示に使用します。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| 出力変数名 | 必須。最終結果のキー名 | `result` |
| 変数のソース | テンプレート式。書き込む値を決定します | `{{previous.output}}` |
| 固定出力値 | 任意。入力すると変数のソースより優先されます | 空 |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

**注意：** 出力ノードはフローの「出口」であり、これ以上出力エッジを持たせるべきではありません。

### 5.7 終了（end）

任意のノードで、終了サマリーのテンプレートを生成するために使用します（ロールにバインドされたフローでは単独で使われることはあまりありません）。

| フィールド | 説明 | デフォルト値 |
|------|------|--------|
| 終了サマリーのテンプレート | `{{outputs.xxx}}` をサポートします | `{{outputs.result}}` |
| 合流方式 | 複数の上流がこのノードに入る際の `previous` の生成方法 | `all_merge` |

## 七、接続線の設定

**接続線** を選択すると、右側で **接続線の条件** を設定できます。

| シーン | 例 |
|------|------|
| 通常ノードの後のフィルタリング | `{{previous.output}} == "ok"` |
| 条件ノードの「はい」分岐 | `{{previous.matched}} == "true"` |
| 条件ノードの「いいえ」分岐 | `{{previous.matched}} == "false"` |

接続線の条件を入力しない場合：

- 条件ノード以外：接続線は常に通過します  
- 条件ノード：出力エッジの順序に従って、はい / いいえの分岐を自動的に割り当てます

## 八、完全な例：条件ノードをまたいでエージェントの出力を渡す

### 7.1 フロー構成

```text
開始 → エージェント（初期値を生成）→ 条件 → エージェント（加工）→ 出力
                              ↘ いいえ → 出力
```

### 7.2 ノード設定

**Agent 1（1 つ目のエージェント）**

| フィールド | 値 |
|------|-----|
| ノードへの指示 | `123333333` のみを出力 |
| 出力変数名 | `agent_result1` |

**条件**

| フィールド | 値 |
|------|-----|
| 条件式 | `{{outputs.agent_result1}} != ""` |

**Agent 2（2 つ目のエージェント）**

| フィールド | 値 |
|------|-----|
| 入力元 | `{{outputs.agent_result1}}` |
| ノードへの指示 | 入力に 100 を加えて出力する |
| 出力変数名 | `agent_result` |

**出力**

| フィールド | 値 |
|------|-----|
| 出力変数名 | `result` |
| 変数のソース | `{{outputs.agent_result}}` |

### 7.3 よくある間違い

| 誤った設定 | 原因 |
|----------|------|
| Agent 2 の入力元に `{{previous.output}}` と記述 | `previous` は条件ノードを指すため、得られるのは `true`/`false` であり、Agent 1 のテキストではありません |
| Agent 1 に出力変数名を入力していない | `outputs.agent_result1` が存在せず、下流が空の値を取得します |
| 条件式に `{{previous.output}}` と記述 | 判定されるのは開始ノードまたは直前のノードの出力であり、Agent 1 の名前付き変数ではありません |

## 九、ロールへのバインドと実行

### 8.1 ロール管理でバインドする

1. **ロール管理** を開き、ロールを編集または新規作成します  
2. バインドする **ワークフロー** の ID を選択します  
3. ポリシーを `auto` に設定します（デフォルト：`workflow_id` がある場合は自動実行）  
4. ロールを保存します

ロールの YAML で直接設定することもできます。

```yaml
name: ワークフローテスト
workflow_id: "1233"
workflow_version: latest
workflow_policy: auto
```

### 8.2 実行時の動作

ユーザーがこのロールを選択してメッセージを送信すると：

1. エンジンが対応する `graph_json` を読み込み、グラフに従って実行します  
2. 会話ページで、`workflow_start`、`workflow_node_start`、エージェントの推論などの進捗イベントを確認できます  
3. フローの終了後にサマリーが返され、`outputs` 内のすべての名前付き出力が一覧表示されます

出力ノードが設定されていない場合や条件に一致しなかった場合は、`outputs` が空になることがあり、その際はサマリーで出力ノードと分岐を確認するよう案内されます。

## 十、デバッグ、ドライラン、振り返り

### 9.1 安全なドライラン（dry-run）

キャンバスのツールバーで **ドライラン** をクリックし、テストメッセージを 1 件入力すると、フローを模擬実行できます。

dry-run の安全境界：

- `start` / `condition` / `output` / `end` は実際のロジックに従って計算されます
- `tool` は MCP を実際には呼び出さず、`[dry-run] tool call skipped` のみを返します
- `agent` は LLM を実際には呼び出さず、`[dry-run] agent execution skipped` のみを返します
- `hitl` は一時停止せず、通過したものとして模擬します

関連 API：

```http
POST /api/workflows/dry-run
```

リクエストボディ：

```json
{
  "graph": { "nodes": [], "edges": [], "config": {} },
  "inputs": { "message": "ping" }
}
```

レスポンスには次の内容が含まれます。

- `outputs`
- `nodeOutputs`
- `trace`
- `metrics`
- `replayScript`

### 9.2 実行詳細と replay

実行後は、ノードごとの完全な実行トレースを照会できます。

```http
GET /api/workflows/runs/{runId}
```

`run` と `nodeRuns` が返され、各ノードのレコードには次の内容が含まれます。

- input スナップショット
- output スナップショット
- status / error
- started_at / finished_at
- `duration_ms`

振り返り用インターフェース：

```http
GET /api/workflows/runs/{runId}/replay
```

このインターフェースは、保存済みの `nodeRuns` のみに基づいてステップを生成し、ツールやエージェントを再実行することはありません。

### 9.3 指標（metrics）

ワークフローは、可能な範囲で次の項目を集計します。

- `node_count`
- `duration_ms`
- `tool_call_count`
- エージェントの progress から収集可能な `prompt_tokens` / `completion_tokens` / `total_tokens` / `cost`

トークンとコストが存在するかどうかは、基盤となるモデル / エージェントのイベントが usage を報告するかどうかに依存します。

## 十一、保存前の検証ルール

保存時に、システムが次の項目を自動的にチェックします。

| ルール | 説明 |
|------|------|
| 開始ノードが必要 | 少なくとも 1 つの `start` |
| 出力ノードが必要 | 少なくとも 1 つの `output` があり、出力変数名が入力されていること |
| 接続が正当 | 接続元 / 接続先ノードが存在し、自己ループでないこと |
| 開始ノードに入力エッジがない | 開始ノードは接続先になれません |
| 出力 / 終了ノードに出力エッジがない | 出力 / 終了ノードの後にさらに接続すべきではありません |
| 開始ノード以外は入力エッジが必要 | 孤立したノードを避けます |
| 出力 / 終了ノード以外は出力エッジが必要 | 実行が行き止まりに到達することを避けます |
| 循環がない | Workflow のオーケストレーションは DAG でなければなりません |
| 到達可能性 | すべてのノードが開始ノードから到達でき、最終的に output/end に到達できること |
| ツールノード | MCP ツールを選択すること。引数 JSON が正当であること。タイムアウトが正の整数であること |
| エージェントノード | ノードへの指示または入力バインドを入力すること。出力変数名を入力すること |
| 条件ノード | 式を入力すること。出力エッジが 1〜2 本必要。分岐にははい / いいえのマークが必要で、重複できません |
| 接続線の条件 | 式、正規表現、JSONPath/JQ パスが静的検証を通過すること |
| 合流方式 | `all_merge` / `last_by_canvas` / `first_non_empty` / `fail_fast` のいずれかであること |

## 十二、トラブルシューティング

| 現象 | 考えられる原因 | 対処の目安 |
|------|----------|----------|
| 下流が空の値を取得する | 上流に出力変数名が設定されていない | 上流のエージェント/ツールに **出力変数名** を入力し、下流では `{{outputs.xxx}}` を使用する |
| 下流が `true`/`false` を取得する | `{{previous.output}}` を誤用しており、直前のステップが条件ノードである | `{{outputs.xxx}}` に変更する |
| 条件が常に「いいえ」に進む | 式と実際の出力形式が一致していない | エージェントの出力に引用符や改行が含まれていないか確認する。まず `!= ""` で検証する |
| フローに最終出力がない | 出力ノードのある分岐に一致しなかった | 条件分岐の接続線を確認する。少なくとも 1 つの経路が **出力** ノードに到達するようにする |
| ロールとの会話でフローが実行されない | ロールがバインドされていない、または有効化されていない | `workflow_id`、`workflow_policy: auto`、フローの `enabled: true` を確認する |
| ツールノードが失敗する | 引数 JSON が不正、またはツールが有効化されていない | 引数テンプレートを確認する。MCP で該当ツールを有効化する |
| 保存時に分岐が不正と表示される | 条件ノードの出力エッジにはい/いいえのマークがない、または重複している | 接続線を選択し、条件分岐を `true` または `false` に設定する |
| 複数の上流の結果が想定と異なる | 合流方式が適切でない | シーンに応じて `all_merge` / `first_non_empty` / `last_by_canvas` / `fail_fast` に変更する |
| ネストしたフィールドが取得できない | JSONPath/JQ パスが安全なサブセットに適合していない | `$.a.b[0]` または `.a.b[0]` を使用し、ワイルドカード/再帰/式は使用しない |

## 十三、ベストプラクティス

1. **命名規約**：参照される各ノードに、`scan_result`、`parsed_targets` のような意味のある出力変数名を設定し、すべてを `agent_result` にしないようにします。  
2. **ノードをまたぐ受け渡しは `outputs` を優先**：間に条件、ツール、承認ノードが挟まる可能性がある場合は、名前付き変数を使用します。  
3. **`previous` は直接接続のみに使用**：A → B で間にノードがない場合は、`{{previous.output}}` が最も簡潔です。  
4. **条件判定ではソースデータを参照**：エージェントの出力を判定するときは `{{outputs.xxx}}` を使用し、`{{previous.output}}` は使用しません（条件が対象エージェントの直後にある場合を除く）。  
5. **すべての経路に出口を用意**：「はい」「いいえ」の分岐がいずれも最終的に **出力** ノード（または想定する終点）に到達するようにします。  
6. **複数の上流を持つノードでは合流方式を明示的に選択**：結果の統合には `all_merge`、フォールバックには `first_non_empty`、重要なチェーンには `fail_fast` を使用します。  
7. **ネストした JSON には JSONPath/JQ の安全なパスを使用**：例：`jsonpath({{previous.output}}, "$.status") == "ok"`。  
8. **保存前にまず dry-run**：単純なメッセージでデータの受け渡しと分岐を検証してから、ロールにバインドして実際に実行します。
