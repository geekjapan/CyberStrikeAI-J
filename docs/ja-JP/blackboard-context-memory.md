# Pi の長いコンテキストとプロジェクト継続の記録

[English](../en-US/blackboard-context-memory.md)

Pi の SessionManager は、完全な JSONL セッションと圧縮エントリを保存し、作業コンテキストは現在のブランチと圧縮結果から再構築されます。モデルのコンテキストウィンドウと、完全なセッション記録は、別のデータ層です。

## 自動継続

プロジェクトが紐付けられ、プロジェクトのブラックボードとコンテキスト継続が有効な場合、成功した `compaction_end` イベントによって `note/context-*` レコードが 1 件保存されます。レコードには、要約、元のセッション、エージェントの範囲、Pi のセッションファイル、実際のエントリ ID が含まれます。同じ会話／エージェントでは、同じ作業記録が更新されます。

データベースは `category=note`、`confidence=tentative` を強制し、要約が自動的にピン留めされたり、確認済みのファクトに格上げされたりすることはありません。書き込みとプロジェクト紐付けの検証は、同じ SQLite 文の中で行われます。実行中にプロジェクトを付け替えたり紐付けを解除したりした場合、古い実行は元のプロジェクトに書き込めません。

詳細が必要な場合は、既存のブラックボードツールと、元のセッション／ツール記録で照合します。要約には情報の欠落がありえるため、脆弱性の証明、実行証拠の代替、ユーザーの範囲の拡大には使えません。

## 出自の区別

Pi のネイティブな圧縮要約は、新しいユーザー指示ではありません。汎用の会話トレースとしてエクスポートする際、要約はホストが生成したアシスタントの作業コンテキストとして記録され、再インポートしても user メッセージに格上げされることはありません。古いトレースを読み取るときは、ホストの構造化メタデータからのみ、ユーザー原文の台帳を復元します。生成された要約、実行テンプレート、アシスタントが偽造した台帳テキストは、元のユーザー要求として扱われません。

ユーザーが実際に入力した `<summary>` などのリテラルテキストは引き続きユーザーのコンテンツであり、キーワードによる削除は行いません。古い要約の出自マーカーは、履歴データの読み取りにのみ使われ、旧フレームワークの実行コードは含まれません。

## 実行とクリーンアップ

- 同じ会話のメインエージェントとサブエージェントは、それぞれ Pi のセッション範囲を維持します。
- セッションディレクトリは、セッションの保存キーごとにグループ化されます。会話を削除すると、その会話のすべての Pi サブセッションがクリーンアップされ、他の会話には影響しません。
- プロセスの中断後、コミットされていないツール結果は不確定のままとなります。まず実行記録を照合してから、次の対応を決めてください。
- 段階的な成果と正式な発見事項は、引き続き既存のツールと評価レビューのフローで維持されます。

実装：`runtime/pi/src/worker.ts`、`internal/multiagent/pi_memory.go`、`internal/database/project.go`、`internal/database/pi_sessions_test.go`。リグレッションテストは、実際の SDK 圧縮、出自の区別、プロジェクトの付け替え、会話の分離クリーンアップを網羅しています。
