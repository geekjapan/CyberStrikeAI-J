# コントリビューションガイド

[English](../en-US/contributing-guide.md) | [中文](../zh-CN/contributing-guide.md)

本書は、CyberStrikeAI に機能、インターフェース、ツール、フロントエンドのページ、またはドキュメントを追加する際の基本要件を定めます。

## 基本原則

- 新機能にはドキュメントの入口を設ける。
- 新しい API では OpenAPI を更新する。
- 新しいフロントエンドの文言には、中国語と英語の i18n を追加する。
- 新しい設定では、ホット適用に対応しているかを説明する。
- 新しい高リスクツールでは、HITL ポリシーを説明する。
- 新しいデータベースフィールドは、旧データベースと互換性を保つ。
- 新しい長時間タスクには、状態、キャンセルまたは復旧のポリシーを設ける。

## 新規 API のチェックリスト

- Handler のパラメーター検証が明確である。
- エラーレスポンスに、安定した `error` と読みやすい `message` が含まれている。
- プラットフォームからのコールバックであることが明確な場合を除き、インターフェースが認証で保護されている。
- 変更系のインターフェースが監査を記録する。
- 長時間タスクが監視またはタスク状態を記録する。
- `internal/handler/openapi.go` を更新する。
- API ドキュメントまたは Recipe を更新する。
- Handler のテストを追加する。

## 新規設定のチェックリスト

- `config.Config` 構造体にフィールドがある。
- `config.example.yaml` のサンプルにコメントがある。
- フィールドが省略された場合に、安全なデフォルト値がある。
- 旧設定で起動できる。
- ホット適用に対応しているかを説明する。
- Web の設定ページが未知のフィールドを誤って削除しない。
- 高リスクの機能に影響する場合は、セキュリティドキュメントを更新する。

## 新規ツールのチェックリスト

YAML ツールと Go の組み込み MCP ツールの両方に適用されます。

- ツール名が安定していて具体的であり、重複を避けている。
- `short_description` が `tool_search` で検索できる。
- 入力 schema が明確で、素の `cmd` ですべての動作を包んでいない。
- 出力が読みやすく、構造が安定している。
- タイムアウトとエラーパスを制御できる。
- 高リスクの操作をグローバルなホワイトリストに入れない。
- ドキュメントで、利用シーンとリスクを説明している。

## 新規フロントエンドページのチェックリスト

- 既存の `apiFetch`、modal、通知、状態のスタイルを再利用する。
- 表示されるすべての文言について、`zh-CN.json` と `en-US.json` を補う。
- loading、empty、error の状態がある。
- 削除や高リスクの操作に確認がある。
- 長い文章や英語のボタンがはみ出さない。
- ブラウザーのコンソールにエラーがない。

## 新規データベース変更のチェックリスト

- マイグレーションが冪等である。
- 旧データベースをアップグレードできる。
- フィールドのデフォルト値が妥当である。
- 大きなテーブルへのインデックスは慎重に扱う。
- 空のデータベースと旧データベースをテストする。
- リリースノートでバックアップを促す。

## 新規高リスク機能のチェックリスト

高リスクには、Shell、WebShell、C2、外部 MCP の書き込み／実行、認証情報へのアクセス、バッチスキャンが含まれます。

次の問いに答える必要があります。

- 誰が呼び出せるか。
- HITL は必要か。
- 監査では何を記録するか。
- どのようにキャンセルするか。
- どのようにクリーンアップするか。
- どのように無効化するか。
- デフォルトでは無効か。

## ドキュメントの要件

公開リポジトリには、ユーザーまたはコントリビューター向けの長期的なドキュメントのみを残します。内部のタスク段階の記録、会話での確認、一回限りの問題確認表、レビューの草稿、ローカルでの検証の記録は、リポジトリの外に保存してください。引き続き有用なインターフェースの規約、互換性の説明、設計上の境界は、正式なガイドにまとめてください。修正の概要は `CHANGELOG.md` に書き、プロセスの記録をプロダクトのドキュメントの代わりにしないでください。

重要な機能には、少なくとも次を補います。

- 用途。
- 設定。
- 操作フロー。
- リスクの境界。
- トラブルシューティング。
- ソースコードのアンカー。

同じトピックの中国語版と英語版のドキュメントは同じファイル名を使い、それぞれ次のディレクトリに置きます。翻訳がまだない場合は、リンク切れを避けるため、ナビゲーションで既存の言語を明示してください。

```text
docs/zh-CN/
docs/en-US/
```

ナビゲーションの更新：

- `docs/README.md`
- `docs/zh-CN/README.md`
- `docs/en-US/README.md`

ドキュメントの変更をコミットする前に、ローカルリンク、コードブロックの閉じ忘れ、中国語版と英語版のファイル名の対応、言語ナビゲーションのカバレッジ、およびルートの README にある Go のバージョンが `go.mod` と一致していることを確認してください。バージョンを含むサンプルは、できる限り `go.mod`、`config.example.yaml` などの権威あるファイルから導出し、手作業での同期を避けてください。

## レビューの着眼点

コードレビューでは、次の点を優先して確認します。

- 動作のリグレッション。
- セキュリティの境界。
- 旧データとの互換性。
- エラー処理。
- テストの不足。
- ドキュメントと OpenAPI が同期されているか。
