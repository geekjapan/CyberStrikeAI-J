# Agent とロールのガイド

[English](../en-US/agent-and-role-guide.md)

CyberStrikeAI の Agent の動作は、ロール、サブエージェント、Skills の 3 種類のリソースによって決まります。ロールは現在のタスクにおける役割と使用可能なツールを決定し、サブエージェントはマルチエージェントでの分担を決定し、Skills は必要に応じてロードできるテーマ別の知識と手順を提供します。

## ロール

ロールファイルは `roles/` にあり、形式は YAML です。ロールには通常、次が含まれます。

- 名前。
- 説明。
- システムプロンプト。
- 使用可能なツールのリスト。

設計原則：

- 専用ロールには、必要なツールだけを紐づける。
- プロンプトで認可の境界を明確にする。
- 高リスクな操作については、先に影響を説明させ、承認を待たせる。
- 出力形式はできるだけ安定させ、レポートや振り返りをしやすくする。

例の方向性：

- 情報収集。
- Web アプリケーションのスキャン。
- API セキュリティテスト。
- クラウドセキュリティ監査。
- デジタルフォレンジック。
- バイナリ解析。
- CTF。

## シングルエージェント

シングルエージェントのインターフェース：

- `POST /api/agent`
- `POST /api/agent/stream`

適しているもの：

- 簡単な質疑応答。
- 単一の対象に対するテスト。
- ツールチェーンが短いタスク。
- 安定したコンテキストが必要な対話的な分析。

## マルチエージェントモード

マルチエージェントのインターフェース：

- `POST /api/multi-agent`
- `POST /api/multi-agent/stream`

オーケストレーションモード：

- `deep`：メインエージェントがタスクを分解し、必要に応じてサブエージェントを呼び出す。
- `plan_execute`：先に計画し、その後に実行し、必要に応じて再計画する。
- `supervisor`：スーパーバイザーエージェントが進捗に応じて、異なるサブエージェントへ引き継ぐ。

適しているもの：

- 複数フェーズのペネトレーションテスト。
- 広範囲の情報収集。
- ロールの並列的な分担が必要な分析。
- 長時間タスクやバッチタスク。

## サブエージェントの Markdown

サブエージェントは `agents/*.md` にあります。Front matter の例：

```yaml
---
name: Attack Surface Enumeration
id: attack-surface-enumeration
description: ターゲットの露出面を列挙し、検証可能な手がかりを整理する
tools:
  - subfinder
  - nmap
  - http-framework-test
bind_role: Information Gathering
max_iterations: 300
---
```

本文にはシステムプロンプトを記述します。次を含めることを推奨します。

- 責務の境界。
- 期待する入力。
- ツールを使用する順序。
- 出力形式。
- 禁止事項。

## メインエージェント

メインエージェントには次を使用できます。

- `agents/orchestrator.md`
- `agents/orchestrator-plan-execute.md`
- `agents/orchestrator-supervisor.md`

または、front matter に `kind: orchestrator` を設定します。各オーケストレーションにつき、メインエージェントの定義は 1 つだけにしてください。

## ツールの選択

ツールを選択する順序の推奨：

1. ロールに最小限のツールセットを紐づける。
2. サブエージェントがタスクに応じて専用ツールを追加する。
3. `tool_search` で大量のツールを動的にアンロックする。
4. 高リスクなツールは HITL で承認する。

すべてのロールにすべてのツールをデフォルトで紐づけないでください。コンテキストのコストと誤呼び出しのリスクが、どちらも上昇します。

## プロンプトの推奨事項

良いロールのプロンプトでは、次を説明するべきです。

- 認可された範囲内でのみ行動する。
- まず対象と制約を確認する。
- 書き込み、削除、ブルートフォース、永続化、C2、WebShell などの操作では承認を求める。
- 検証可能な証拠を出力する。
- 不確かな場合は仮定であることを明記し、結果を捏造しない。

## デバッグ

Agent が誤ったツールを選ぶ場合：

- ロールのツールリストを絞り込む。
- ツールの `short_description` を強化する。
- `tool_search_always_visible_tools` を有効にする、または調整する。
- ロールのプロンプトで、ツールを使用する順序を明記する。

マルチエージェントが逸脱する場合：

- サブエージェントの説明が広すぎないか確認する。
- `sub_agent_user_context_max_runes` を下げる、またはタスクの入力を明確にする。
- orchestrator のプロンプトを最適化する。
- プロセスの詳細とツール実行の監視を確認する。

## ロール、サブエージェント、Skill の責務の境界

この 3 つはしばしば混同されるため、次のように分担することを推奨します。

| リソース | 解決する問題 | 担わせるのに適さないもの |
| --- | --- | --- |
| Role | 現在の会話における役割、口調、ツールの境界、認可のルール | 大量の参考資料 |
| Agent Markdown | マルチエージェントにおける専門的な分担、引き継ぎの形式、局所的な方針 | 一度きりのタスクのファクト |
| Skill | 再利用可能な方法論、チェックリスト、テンプレート、長い参考資料 | 権限の制御 |

認可の境界を Skill に書き込み、ロールがツールを制限していない場合、Skill をロードする前に Agent が誤ったツールを選ぶ可能性があります。権限の境界は、まず Role と HITL に置くべきです。

## オーケストレーションモードの選択

| モード | 適しているもの | 適さないもの |
| --- | --- | --- |
| `single` | 短いタスク、対話的な分析、安定したコンテキストが必要なもの | 複数フェーズの大きなタスク |
| `deep` | メインエージェントがタスクを動的に分割し、サブエージェントが必要に応じて深掘りする | 厳密な手順の順序が必要なフロー |
| `plan_execute` | 明確なフェーズがあり、実行後の振り返りと再計画が必要なもの | ユーザーが頻繁に割り込む即興の会話 |
| `supervisor` | 専門家の分担が明確で、スーパーバイザーによるルーティングが必要なもの | サブエージェントの定義が曖昧、または多すぎる場合 |

経験上、通常のセキュリティテストではまず `single` を使い、複雑なプロジェクトでは `plan_execute` を、複数の専門ロールが必要な場合は `deep` または `supervisor` を使用します。

## ツールの可視性が動作に与える影響

マルチエージェントでは、`tool_search` により、モデルは最初は常時表示されるツールの一部しか見えません。その結果は次のとおりです。

- ツールのページで利用可能と表示されていても、モデルの現在のコンテキストで見えているとは限らない。
- `tool_search_always_visible_tools` に含まれるツールは、モデルに呼び出されやすい。
- ツールの説明が明確なほど、検索にヒットしやすい。
- サブエージェント自身の `tools` による制限は、依然として重要である。

「Agent がなぜあるツールを使わないのか」をデバッグするときは、ロールのツール、サブエージェントのツール、tool_search の設定、ツールの説明を、あわせて確認する必要があります。

## 良いサブエージェントの出力形式

サブエージェントは、「完了しました」だけを返してはいけません。固定の形式を推奨します。

```markdown
## 結論

## 証拠
- コマンド/ツール：
- 主要な出力：
- 確信度：

## リスク

## 推奨される次のステップ
```

こうすることで、メインエージェントがオーケストレーションを続けられ、攻撃チェーンやプロジェクトのファクトの蓄積にも役立ちます。
