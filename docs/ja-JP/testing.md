# テストガイド

[English](../en-US/testing.md)

CyberStrikeAI のテストには、Go の単体テスト、設定の検証、API の手動テスト、MCP ツールの検証、フロントエンドのスモークテストが含まれます。

## Go 単体テスト

すべての内部テストを実行します。

```bash
go test ./internal/...
```

特定のパッケージを実行します。

```bash
go test ./internal/workflow
go test ./internal/multiagent
go test ./internal/handler
```

主な重点パッケージ:

- `internal/security`
- `internal/mcp`
- `internal/multiagent`
- `internal/workflow`
- `internal/knowledge`
- `internal/project`
- `internal/handler`
- `internal/c2`

## ビルドテスト

```bash
go build -o cyberstrike-ai ./cmd/server
```

ビルドが通ったからといって機能が正しいとは限りませんが、エントリーポイント、依存関係、静的型の問題を発見できます。

## 設定の検証

起動前に次を確認します。

- YAML のインデント。
- モデルの設定。
- データベースのパスが書き込み可能であること。
- `tools_dir`、`roles_dir`、`skills_dir`、`agents_dir` が存在するか。
- HTTPS 証明書のパスが正しいか。

起動後、Web の設定ページで次をテストします。

- OpenAI 互換モデル。
- ビジョンモデル。
- ツール一覧。
- 外部 MCP の状態。

## API の手動テスト

次にアクセスします。

```text
/api-docs
```

重点的に検証する項目:

- ログイン。
- `/api/agent/stream`。
- `/api/config`。
- `/api/config/tools`。
- `/api/knowledge/search`。
- `/api/monitor`。

ストリーミングインターフェースがリバースプロキシを経由する場合は、出力がリアルタイムに届くかを検証する必要があります。

## ツールのテスト

`tools/*.yaml` を追加または変更した後:

- ツール一覧でスキーマを確認する。
- 低リスクのパラメーターで実行する。
- エラー出力が読みやすいか確認する。
- タイムアウトが有効に機能するか確認する。
- HITL が想定どおりにブロックするか確認する。

本番ターゲットで新しいツールをテストしないでください。

## MCP のテスト

外部 MCP:

- stdio: まずターミナルでコマンドを単独で実行する。
- HTTP/SSE: curl で疎通を確認する。
- Web ページの起動後に `/api/external-mcp/stats` を確認する。
- 会話の中で、ツールが `tool_search` で見つかるか確認する。

## ナレッジベースのテスト

手順:

1. 小さな Markdown ドキュメントを配置する。
2. ナレッジベースをスキャンする。
3. インデックスを再構築する。
4. ドキュメント内のキーワードと同義表現を検索する。
5. 検索ログを確認する。

実際の embedding API を使用する場合は、クォータとレート制限に注意してください。

## フロントエンドのスモークテスト

フロントエンドを変更した後は、少なくとも次を検証します。

- ログインとログアウト。
- サイドバーの会話リスト。
- 新規会話の作成とストリーミング応答。
- 設定ページの保存。
- 関連する業務ページの作成・削除・更新・参照。
- 英語と日本語の切り替え。
- ブラウザーのコンソールに目立つエラーがないこと。

## 高リスクモジュールのテスト

C2、WebShell、ターミナル、バッチタスクは、許可されたテスト環境でのみ検証してください。テスト前に次を確認します。

- ターゲットがローカルマシン、ターゲットマシン、または演習環境であること。
- コマンドが破壊的でないこと。
- HITL ポリシーが想定どおりであること。
- テスト後に、セッション、payload、アップロードしたファイル、タスク結果をクリーンアップすること。

## テストピラミッド

テストは次のように階層化することを推奨します。

| 階層 | 目的 | 例 |
| --- | --- | --- |
| 単体テスト | 純粋なロジックが正しいこと | 式、chunk、マスキング、タイムアウトの形式 |
| Handler テスト | HTTP の動作 | パラメーターの検証、ステータスコード、権限 |
| 統合テスト | 複数モジュールの連携 | 外部 MCP、ナレッジベースのインデックス、HITL |
| スモークテスト | ユーザーの操作経路が使えること | ログイン、会話、ツール、設定 |
| 認可済み演習環境でのテスト | 高リスク機能の安全性 | C2、WebShell、ターミナル |

エンドツーエンドの手動テストで単体テストの代わりにしたり、単体テストで高リスクの演習環境での検証の代わりにしたりしないでください。

## 回帰テストの重点

次のモジュールを変更する場合は、テスト範囲を必ず広げてください。

- `internal/handler/config.go`: モデル、ナレッジベース、MCP、C2、ボット設定の適用をテストする。
- `internal/multiagent/`: ストリーミング、ツール呼び出し、要約、リトライ、HITL をテストする。
- `internal/security/`: 認証、Shell、タイムアウト、出力なしをテストする。
- `internal/database/`: 旧データとの互換性をテストする。
- `web/frontend/src/pages/chat/`: 会話、プロセスの詳細、攻撃チェーン、グループをテストする。

## テストデータの管理

実際の顧客データでテストしないでください。次を用意することを推奨します。

- 小さな Markdown ナレッジベースのサンプル。
- ローカルの偽の MCP Server。
- ローカルで制御可能な HTTP ターゲット。
- 無害な WebShell のシミュレーター。
- 一時的な SQLite データベース。

テスト完了後は一時データベースとアップロードしたファイルを削除し、開発環境が汚染されないようにしてください。

## 成功ケースより失敗ケースが重要

少なくとも次をカバーしてください。

- モデル API の 401/429/500。
- MCP プロセスの起動失敗。
- ツールのタイムアウト。
- HITL による拒否。
- ナレッジベースのインデックス作成の中断。
- データベースが書き込み不可。
- WebShell のターゲットが 200 以外を返す。
- C2 が無効のときにインターフェースへアクセスする。

これらこそ、ユーザーが実際に遭遇する問題です。
